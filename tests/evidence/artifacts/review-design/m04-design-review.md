## Findings

### M04-D01 — blocking — Define how one runtime manages several environment identities

**Location:** [docs/architecture/m04-plan.md:64](docs/architecture/m04-plan.md:64) and [docs/architecture/m04-plan.md:379](docs/architecture/m04-plan.md:379); [docs/decisions/0010-platform-realization.md:124](docs/decisions/0010-platform-realization.md:124).

**Problem:** An endpoint target is insufficient to create usable WSL/container bindings. The present application rejects a requested environment different from its configured environment in both authority loading and resolution ([crates/app/src/operations.rs:6159](crates/app/src/operations.rs:6159), [crates/app/src/operations.rs:4215](crates/app/src/operations.rs:4215)), rejects continuing grants belonging to another environment ([crates/app/src/operations.rs:1550](crates/app/src/operations.rs:1550)), and skips their operations during restart recovery ([crates/app/src/operations.rs:5806](crates/app/src/operations.rs:5806)). The issuer's independent check obtains the single store self-environment ([crates/app/src/operations.rs:12365](crates/app/src/operations.rs:12365)). Materialized slots also explicitly assume one environment per state directory ([crates/adapters/src/managed/files.rs:608](crates/adapters/src/managed/files.rs:608)). M04 proposes distinct environment records while retaining the Windows runtime/issuer, but describes its application changes as dispatch arms and one call each. Simply removing the equality checks would weaken the existing authority boundary.

**Change:** Add an integrator-owned design for the runtime's managed-environment set, the target-environment lookup and ownership check, per-environment slot/projection namespaces, issuer validation, recovery and cleanup. Keep the authenticated controller principal distinct from the execution environment. Assign this application work explicitly alongside M05's activation/delegation work; it cannot be hidden in endpoint creation. Reuse existing authority tests, extending the real ensure→issue→bind→sign→restart path to native plus WSL/container environments, with an unmanaged/removed environment refused and one environment's cleanup leaving the other usable.

### M04-D02 — blocking — Carry the projection transaction across the WSL channel

**Location:** [docs/architecture/m04-plan.md:148](docs/architecture/m04-plan.md:148); [docs/decisions/0010-platform-realization.md:136](docs/decisions/0010-platform-realization.md:136) and [docs/decisions/0010-platform-realization.md:165](docs/decisions/0010-platform-realization.md:165).

**Problem:** U3 promises to reuse M02's apply/rollback machinery inside the distribution, while U0 freezes a protocol whose listed messages contain only Realize/Withdraw and agent streams. The reused writer requires a durable `StageSink`: each receipt must be persisted before proceeding, and item commit must be durable before settlement ([crates/app/src/ports.rs:513](crates/app/src/ports.rs:513), [crates/app/src/ports.rs:661](crates/app/src/ports.rs:661)). Recovery accepts the stored intent and receipts ([crates/app/src/ports.rs:673](crates/app/src/ports.rs:673)); it is not another unconditional apply. With no durable helper state and no specified receipt/acknowledgment or recovery exchange with Windows, an ordinary crash or lost channel after a Git/config exchange can leave an unrecorded mutation or lock. The existing local transaction tests do not exercise this new distributed failure boundary. Likewise, disable/uninstall of a stopped distribution has no specified outcome, while background startup is forbidden except for explicit ensure ([docs/decisions/0010-platform-realization.md:172](docs/decisions/0010-platform-realization.md:172)).

**Change:** Before freezing `heimdall-wsl/1`, define the minimal file-operation requests and durable receipt/item-commit acknowledgments, their bounds and cancellation rules, and reconciliation after a lost reply. Keep the journal on Windows if the helper owns nothing durable. Specify stopped-distribution cleanup as an explicit authorized start or a retained, reported cleanup obligation; do not discard ownership or claim successful rollback. Extend one existing projection fault scenario over the real helper channel: interrupt after exchange/before durable receipt or commit, restart, reconcile, preserve a subsequent user edit, and remove only the recorded generation. Happy-path enable/disable and a Withdraw unit test do not prove this.

### M04-D03 — blocking — Realize catalog host trust at both ProxyJump hops

**Location:** [docs/decisions/0010-platform-realization.md:294](docs/decisions/0010-platform-realization.md:294); [docs/architecture/m04-plan.md:232](docs/architecture/m04-plan.md:232) and [docs/architecture/m04-plan.md:249](docs/architecture/m04-plan.md:249).

**Problem:** The ADR claims each hop's host key comes from the catalog, but U6 only adds ProxyJump/ForwardAgent rendering and a dependency check. Existing P deliberately inherits host verification and cannot render host-trust directives ([docs/decisions/0007-existing-access-integration.md:119](docs/decisions/0007-existing-access-integration.md:119); [crates/sshconf/src/render.rs:9](crates/sshconf/src/render.rs:9)). Managed connect adds identity and foreground options, not catalog host-key pins ([crates/heimdall/src/connect_cmd.rs:442](crates/heimdall/src/connect_cmd.rs:442)). The pinned known-hosts line in the enrollment layer is for its dedicated enrollment/verification steps ([crates/app/src/enrollment.rs:605](crates/app/src/enrollment.rs:605)), not ordinary SSH through P. A final-host substitution test with an ordinary fixture known_hosts file could pass without exercising the claimed catalog binding, and does not test substitution of the bastion.

**Change:** Specify how both the jump subprocess and final client obtain the approved host binding, or narrow the claim explicitly to OpenSSH's existing user-controlled host trust. If catalog-pinned trust remains the claim, assign the required renderer/projection/launch changes and the applicable ADR-0007 revision. Extend the route test with separate substituted jump and final keys, plus an inherited alternative trust source (for example KnownHostsCommand), using the actual product-generated configuration. Assert failure before authentication to the substituted hop, rather than supplying test-only pinning flags. This is required by [spec.md:732](spec.md:732) and must also work for ordinary SSH/Git, not only the wrapper.

### M04-D04 — blocking — Direct enrollment followed by a jump loses the existing evidence

**Location:** [docs/architecture/m04-plan.md:438](docs/architecture/m04-plan.md:438); [docs/decisions/0010-platform-realization.md:317](docs/decisions/0010-platform-realization.md:317).

**Problem:** The recommended workaround does not preserve the M03 verified-scope claim. `route_matches` explicitly requires `ProxyRoute::None` ([crates/app/src/enrollment.rs:621](crates/app/src/enrollment.rs:621)), and `evidence_holds` uses that predicate ([crates/app/src/enrollment.rs:688](crates/app/src/enrollment.rs:688)). When inspect/ensure next reads a pair with ProxyJump, the managed adapter invalidates its evidence and reports destination scope unknown; callers requiring the verified guarantee fail ([crates/adapters/src/managed/prepare.rs:251](crates/adapters/src/managed/prepare.rs:251)). U6 does not own this freshness rule. Deferring all verification changes while claiming the directly enrolled destination remains verified through the route therefore contradicts the existing interface.

There is a related consumer gap: managed `connect` requests only the final pair ([crates/heimdall/src/connect_cmd.rs:256](crates/heimdall/src/connect_cmd.rs:256)), whereas the proposed managed-bastion rule requires its pair in the same grant ([docs/decisions/0010-platform-realization.md:300](docs/decisions/0010-platform-realization.md:300)). U6 does not list connect as a caller to update.

**Change:** It is reasonable to defer *remote enrollment mutations* through jumps. Explicitly separate those from the route-aware evidence/freshness and connection work M04 needs: preserve final destination/account/CA verification only after validating the approved route dependency and host identities; keep unrelated/dynamic route changes fail-closed. Define whether connect resolves the approved dependency within the selected profile or reports a deliberate limitation; never silently add scope outside approval. Test the advertised sequence through product operations: direct enroll/verify → configure jump → ensure/inspect with verified-scope requirement → connect via managed and existing-access bastions. Also test an unauthorized dependency and a later jump/key change. Do not seed a pre-verified record that bypasses freshness.

### M04-D05 — non-blocking — Make the container row prove usable scoped signing and expiry

**Location:** [docs/architecture/m04-plan.md:214](docs/architecture/m04-plan.md:214) and [docs/architecture/m04-plan.md:223](docs/architecture/m04-plan.md:223).

**Problem:** The container tests explicitly name rendering, directory contents, UID admission, identity listing/control rejection and endpoint replacement. None explicitly requires successful SSH authentication from the mounted container followed by refusal after expiry. An implementation that lists the right certificates but cannot authenticate because its in-container files or signing session are wrong could satisfy those stated checks. This is particularly relevant because U5 uses a different endpoint/layout path. [spec.md:139](spec.md:139) requires container binding *and expiry behavior*; [spec.md:424](spec.md:424) requires UID and endpoint-state tests. A working signing path is not established by connect/list alone.

**Change:** Fold one permitted SSH login and an unauthorized-key/destination refusal into the existing container integration case, then require fresh authentication to stop at the original deadline and a replacement generation to work at the mounted path. For UID-negative rows, keep an otherwise-identical admitted positive control, so missing mounts/permissions cannot masquerade as peer-credential enforcement. Keep these WSL/test-store results labelled mechanism evidence; the native Linux product row remains blocked on B11. No extra suite is needed.

### M04-D06 — non-blocking — Falsify the time signal before trusting it for reboot recovery

**Location:** [docs/architecture/m04-plan.md:100](docs/architecture/m04-plan.md:100); [docs/decisions/0010-platform-realization.md:347](docs/decisions/0010-platform-realization.md:347).

**Problem:** The Linux mechanism is plausible: systemd v255's `ntp_synced()` really uses `adjtimex` with `maxerror < 16000000`, deliberately ignoring STA_UNSYNC. However, a mapper unit test plus agreement with timedatectl on the current host tests conversion and agreement with the same underlying signal, not its safety when synchronization is absent/failed or after a wrong-clock reboot. Those are the explicit outstanding R9 cases ([docs/decisions/0005-managed-credential-recipe.md:986](docs/decisions/0005-managed-credential-recipe.md:986)). The plan names B12 generically but does not make the trust-enabling decision depend on those records.

**Change:** Specify the mapper's error, units and threshold cases, and make activation of the trusted source conditional on the relevant native signal evidence, including absent/failed synchronization and the B12 wrong-clock reboot case. Until that claim is evidenced, retain Unknown/attended confirmation for the unproven case. Use a disposable machine for disruptive clock/service changes; do not stop the devbox owner's time service to manufacture a negative control. Existing virtual-clock tests already cover the gate itself and should be reused.

Primary-source cross-check, read during this review: [systemd v255 timedated.c, lines 554–563](https://github.com/systemd/systemd/blob/v255/src/timedate/timedated.c#L554-L563). This verifies the stated algorithm, not native behavior on the owner's hosts.

### M04-D07 — non-blocking — Complete the shared-file and integration ownership list

**Location:** [docs/architecture/m04-plan.md:401](docs/architecture/m04-plan.md:401).

**Problem:** The conceptual where/how versus whether/when split is useful, but the claimed complete shared list omits known callers/registration points. The environment work in D01 touches authority, issuer validation and recovery inside Operations, not just dispatch. Route extension derivation is called by [crates/app/src/managed/driver.rs:311](crates/app/src/managed/driver.rs:311) and [crates/app/src/operations.rs:12110](crates/app/src/operations.rs:12110); changes must agree at request creation and independent reserve/issuer/publish validation. Migration registration/versioning is in [crates/store/src/migrations.rs:16](crates/store/src/migrations.rs:16), not just the migration directory or lib module lines. New modules/commands also require shared crate entry points, including [crates/heimdall/src/main.rs:10](crates/heimdall/src/main.rs:10) and [crates/localenv/src/sys/mod.rs:82](crates/localenv/src/sys/mod.rs:82). Managed projection data crosses [crates/localenv/src/projection/mod.rs:108](crates/localenv/src/projection/mod.rs:108), absent from the list. **Change:** Add those concrete integration files and the relevant crate lib/mod/Cargo manifests to integrator ownership, and schedule one coordinated patch for environment resolution/issuance plus the M05 activation/delegation hooks. Include `runtime/src/managed_store.rs` and managed slot/file sources when resolving D01. State that dependency/registration edits are serialized, while implementations stay in track-owned modules. No additional coordination framework is needed. The M05 design is not present in this checkout, so this assesses the proposed split against current callers, not a separately verified M05 implementation.

**Location:** [docs/architecture/m04-plan.md:54](docs/architecture/m04-plan.md:54) and [docs/architecture/m04-plan.md:72](docs/architecture/m04-plan.md:72).

**Problem:** U0 explicitly creates a fail-closed placeholder in every future suite to satisfy the zero-test guard. Four target placeholders and new graph mutants are not independently valuable merely because four target files/new legal edges exist. The existing graph checker already detects cycles and forbidden edges generically ([tools/validation/crate_graph.py:24](tools/validation/crate_graph.py:24)). Combine the container rendering/contents checks into its real mounted-flow case unless the golden establishes an otherwise untested escaping property. Preserve new protocol bounds, cross-boundary cleanup fault tests, native UID tests and the real bastion/forwarding journey; those protect distinct claims.

## Authority and exposure assessment

The chosen boundaries are sound in intent: no global agent service takeover, no persistent SSH_AUTH_SOCK change, user-level attended autostart, explicit inherited-handle lists, managed-only Mode B, signing-only endpoints, no TCP bridge, a read-only container mount containing public data and a binding socket, and ordinary ProxyJump without agent forwarding by default ([docs/decisions/0010-platform-realization.md:15](docs/decisions/0010-platform-realization.md:15), [docs/decisions/0010-platform-realization.md:39](docs/decisions/0010-platform-realization.md:39), [docs/decisions/0010-platform-realization.md:145](docs/decisions/0010-platform-realization.md:145), [docs/decisions/0010-platform-realization.md:232](docs/decisions/0010-platform-realization.md:232)). No design step requires recurring elevation or a public listener. Engine package installation is confined to scratch distributions; product Heimdall does not acquire engine/root privileges.

The same-Windows-user/interoperability and same-UID/container-engine non-guarantees are correctly disclosed ([docs/decisions/0010-platform-realization.md:208](docs/decisions/0010-platform-realization.md:208), [docs/decisions/0010-platform-realization.md:275](docs/decisions/0010-platform-realization.md:275)). An ordinary different Linux UID can be refused while a user with Windows interop can return as the owning account; those are different claims. Forwarded bindings may carry every identity in that binding, not just the immediate next-hop identity, and a compromised forwarding peer can use those identities within server-principal/deadline bounds. That limitation is appropriately explicit. Existing-access bastion credentials remain outside the managed grant's expiry/revocation guarantee.

Generation-tagged cleanup is a correct invariant, but ownership-only teardown is not yet established for interrupted WSL file work (D02). Also, the stable container directory follows the environment's newly authorized binding: document that replacement behavior as an environment endpoint, and do not present it as a permanently pinned old job context (spec's pinned-binding rule is at [spec.md:398](spec.md:398)).

## Inferred mechanisms and platform feasibility

ADR-0010 has four literal [I] occurrences, forming three mechanism questions:

1. **Cross-user Windows exclusion:** native pipe exclusion ([docs/decisions/0010-platform-realization.md:70](docs/decisions/0010-platform-realization.md:70)) and other-account WSL registration exclusion ([docs/decisions/0010-platform-realization.md:206](docs/decisions/0010-platform-realization.md:206)) are plausible. B2 is correctly named. Pipe/SID tests do not prove that another account cannot enter the distribution: retain a distinct native B2 test that attempts that route and observes no binding access, with an owner-account positive control.
2. **Container UID admission:** the proposed SO_PEERCRED rule is plausible for a host-namespace listener: rootful mapped user and rootless owner-mapped root can match, while unmapped sub-UIDs/rootful root do not ([docs/decisions/0010-platform-realization.md:249](docs/decisions/0010-platform-realization.md:249)). U5's two engine cases could falsify it, provided they observe the listener's actual peer UID and perform a permitted operation as the positive control (D05). Record the engine/user-namespace versions; do not infer keep-id support from a rootless-root run.
3. **Linux synchronized-time signal:** the systemd algorithm is accurately described and has a mapper/native-observation test, but the present evidence plan does not adequately falsify unsafe positive reporting (D06). A current devbox reading cannot close the B12 reboot case.

The user Run value, scratch LaunchAgent bootstrap, Linux user unit without lingering, stdio-supervised WSL helper, binding-scoped agent service and host-visible bind directory are plausible on the stated platforms. Resolve a Linux-visible executable path for the bundled helper explicitly and fail with helper_unavailable if automount/architecture/execution permissions do not allow it; do not pass a raw Windows path to Linux `--exec`. No native feasibility result was obtained in this review. The concrete application/protocol/route failures above are supported by current interfaces, not speculation about OS versions.

## Parallelism and leanness

Keep independent W1 tracks and the single contract owner. The proposed crate graph can remain acyclic because wsl implements app ports and runtime wires it; app must not import wsl. The split becomes workable after the shared multi-environment authority seam and missing files in D01/D07 are assigned. Do not let M05 assume every binding belongs to `Operations::environment()` while M04 independently changes that meaning. First-merged migration numbering is fine once registration/version constants and migration tests move with the SQL.

The narrow choices are appropriate: one jump, no engine wrapper, no broad existing-agent relay, no Task Scheduler/SCM alternative, no Docker Desktop claim, and no hardware-custody expansion. D08 identifies removable scaffolding. Reuse existing signer/expiry/parser/generation properties; new end-to-end tests are warranted exactly where the realization introduces a new boundary. Do not add duplicate cryptographic/signature tests just to get an M04-prefixed name. Pairing the happy-path container checks in one mounted journey would reduce test count while improving what is proved.
