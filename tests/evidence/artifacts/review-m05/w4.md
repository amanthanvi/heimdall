## Findings

### M05-W4-R01 — Duplicate bundle keys can hide an authority-bearing value from validation

- **Severity:** medium, parser/coverage defect; **does not block** under ADR-0009 §2.1. A repository-supplied bundle is an in-scope trigger, but the overwritten value never becomes authority. The probe caused no lasting trust/data effect and bypassed no approval. Record this limitation; do not claim that every authority-bearing occurrence in the original JSON is rejected.
- **Location:** [crates/project/src/portable.rs:285](crates/project/src/portable.rs:285), before the authority walk at line 291; caller [crates/app/src/operations/portable_m05.rs:80](crates/app/src/operations/portable_m05.rs:80).
- **Scenario:** a bundle contains `"profiles":[{"policy":{"approve":true}}],"profiles":[]`. Deserializing into `serde_json::Value` first keeps only the second `profiles`. The subsequent authority-key walk cannot see the first occurrence. This contradicts the documented refusal of an authority key at any depth in the whole input, although it does not import that authority.
- **Probe:** built binary, isolated scratch homes, stdin closed: `heimdall --json import <duplicate-shadow.json>` (without `--yes`). Complete input:

  ```json
  {"schema":"heimdall-portable/1","created_at":"2026-11-18T09:00:00Z","redacted":false,"destinations":[],"identities":[],"profiles":[{"policy":{"approve":true}}],"profiles":[],"reestablish":[]}
  ```

  **Observed exit 0, `OK`, 0.191 s**; the runtime was started, because the surviving empty bundle reached its dry-run path. The empty plan was a no-op, not an applied approval. Control: the same nested authority object without a duplicate shadow was **exit 2, `USAGE_ERROR`, 0.008 s**, before runtime contact. An escaped JSON authority key (`"\u0070olicy"`) was also exit 2.
- **Smallest correction:** reject duplicate object keys while decoding the raw JSON, before converting it into the value tree. One regression should put an authority-bearing object in the overwritten occurrence. Do not add a second authority system.

### M05-W4-R02 — The bundle FIFO fix does not cover other blocking CLI input files

- **Severity:** medium, availability; **does not block** under ADR-0009 §2.1. An ordinary user following repository instructions can select the FIFO, but the demonstrated effect is a blocked local command. Neither test changed remote trust, recovery records, or owner data, nor bypassed consent.
- **Locations:** [crates/heimdall/src/catalog_cmd.rs:340](crates/heimdall/src/catalog_cmd.rs:340), `read_public_key`; [crates/heimdall/src/service_cmd.rs:88](crates/heimdall/src/service_cmd.rs:88), `load_config`.
- **Scenario:** an agent tells the user to adopt `repo/key.pub`, which is a FIFO with no writer. `File::open` blocks before the byte bound can help. Likewise, a FIFO at the scratch installation's `config/config.toml` blocks `service run` before initialization completes. Controlling an existing owner's config directory additionally requires same-user access; no stronger adversary is inferred.
- **Probes:** `heimdall --json identity adopt --pub <scratch FIFO>` and, separately, `heimdall --json service run` with a scratch FIFO config. **Both remained blocked for 3 s**, emitted zero stdout/stderr bytes, and were killed through their own `Popen` handles; **config child return code -9**. These are timeout observations, not product-generated usage exits. The public-key wrapper recorded `timeout-killed` rather than preserving a numeric child exit; the config probe recorded the signal exit explicitly.
- **Smallest correction:** apply the existing bounded regular-file/open-handle pattern to these reads, with a nonblocking open on Unix and an opened-handle type check. Preserve any intentional regular-file symlink compatibility explicitly. This finding does not require reopening unrelated old file readers in this wave.

### M05-W4-R03 — A29 runtime cleanup is not armed during its startup assertions

- **Severity:** medium, fixture/process hygiene; **does not block** under ADR-0009 §2.1. This is a disposable-test failure path, with no demonstrated lasting owner-data/trust effect or consent bypass.
- **Location:** [tests/adversarial/prompt_injection/cli.rs:185](tests/adversarial/prompt_injection/cli.rs:185), through guard assignment at line 194; `Rt::drop` only drops an already-present guard.
- **Scenario:** the start command has launched the runtime, then an assertion, advertisement read, or process-start observation fails before `self.guard = Some(...)`. `Rt` unwinds with `guard: None` and removes its scratch home while the daemon remains alive. This is narrower than the module's claim that every panic path is guarded.
- **Probe:** temporary fault injection immediately before guard assignment, with a test that catches the panic, checks the exact advertised PID/start token, and verifies its executable through `ProcessPin`. **Exit 101, 0 passed / 1 failed / 9 filtered**. Observed `leaked=true`. The probe then killed the verified exact PID and waited for it to disappear before asserting failure (`exact_pid_cleaned=true`). This intentionally failing test established the defect; it was not left installed. Source restored byte for byte.
- **Smallest correction:** arm cleanup before the startup command can create a daemon, or give `Rt::drop` a scratch-home `service stop` fallback even when the PID guard was never installed. Keep the verified exact-PID fallback for an advertised process. Add one startup-failure regression, reusing this fixture.

## 2. Completeness of the product fixes

**A29-F1 works for the demonstrated portable-bundle FIFO defect on Unix.** There is a pre-open type check, Unix nonblocking open, opened-handle regular-file check and max+1 read. My revert proof removed only the F1 change by restoring the pre-range `portable_cmd.rs`, then restored the reviewed bytes and reran the same test.

It is not a general no-symlink rule: `metadata` and `OpenOptions` follow a symlink to a regular bundle. A separate real-binary probe of such a symlink returned **exit 0, `OK`** for an empty bundle. There is no documented authority gain from reading an owner-selected linked regular bundle. A link to `/dev/zero` is rejected by the new suite. An import read racing a regular-file replacement is not an identity-pinning guarantee; Unix NONBLOCK prevents the FIFO-open stall, while an unusual device swapped between checks is still not proven side-effect-free by this fix. Windows has no equivalent new NONBLOCK flag here; no native race claim was tested.

**Other paths:** export `--out` uses `create_owner_only_exclusive` (`O_EXCL|O_NOFOLLOW` on Unix). My existing-FIFO and dangling-symlink output probes both returned **exit 2** promptly; neither target was replaced. Manifests and `.git` pointer reads use `RealFs::read_regular_nofollow`, bounded bytes and Unix `O_NOFOLLOW|O_NONBLOCK|O_NOCTTY`; manifest special-file cases passed. Public-key/config readers remain blocking as R02 records. The older enrollment recovery-bundle reader also has metadata-then-`fs::read` rather than a bounded opened-handle read ([enroll_cmd.rs:776](crates/heimdall/src/enroll_cmd.rs:776)); its replacement race is source inference, not a new executed probe. `shell init` has **no file target**: it prints static script bytes or a JSON envelope and edits no rc file. Shell redirection to a FIFO is the shell's open, outside this handler.

**A29-F2 works for the three variables it validates as ordinary string values.** Every numeric use is preceded by digit/length/leading-zero checks; state uses a fixed token list; cwd is one quoted argument. The scripts parse returned fields and do not eval them. `command heimdall` bypasses a shell function of that name, but PATH itself remains shell/user authority.

I generated both scripts through the binary and ran them in scratch `HOME` shells with an env-clear environment, bash `--noprofile --norc` and zsh `-f`. Hostile sequence/state/due values plus a cwd containing newline and U+202E completed with **exit 0, no stderr, no marker** (0.022 s bash / 0.036 s zsh). I then set hostile due **after** initialization, forced bash's unchanged-PWD branch and directly called zsh's due check: both exit 0, no stderr or evaluation. With no runtime, both generated integrations exited 0 silently and created no Heimdall home. Existing CLI tests additionally run the scripts interactively on pipes.

This does not sandbox existing shell prompt code. A pre-existing bash `PROMPT_COMMAND="sleep 2"` or zsh `precmd() { sleep 2; }`, with the generated integration loaded, still took **2.025 / 2.028 s**, both exit 0. Existing prompt code can also prompt or run an effectful command that starts a runtime; that is already executable shell configuration, not text newly evaluated by Heimdall. Arbitrary PATH replacement, BASH_ENV/ZDOTDIR startup code and same-user shell variable attributes are not stronger boundaries supplied by F2. No prompt, command-text execution, runtime startup or budget overrun attributable to the actual generated hook was observed in my hostile-data probes. The passing `e2e_hook_m05` independently covers the real default warm-up, refusal, and no-runtime paths.
