### M05-W3-R01 — High; blocking: the setup offer can approve destinations absent from its disclosure

**Locations:** [setup_cmd.rs:522](crates/heimdall/src/setup_cmd.rs:522), [setup_cmd.rs:533](crates/heimdall/src/setup_cmd.rs:533), [setup_cmd.rs:547](crates/heimdall/src/setup_cmd.rs:547). The server captures the profile revision in [trust_m05.rs:440](crates/app/src/operations/trust_m05.rs:440) and applies that snapshot in [trust_m05.rs:1776](crates/app/src/operations/trust_m05.rs:1776). Its decision view contains only the `Create` action, without that snapshot's concrete scope: [operations.rs:5469](crates/app/src/operations.rs:5469).

**Scenario:** setup reads profile `review`, containing only `h1:deploy`. Before its `Create {default: true}` request reaches the server, another ordinary owner catalog edit adds `h2` and `h3`. The server correctly fixes its decision to the newer profile snapshot. The offer nevertheless constructs its disclosure from the earlier listing. The subsequent recorded-request display names the profile, environment and default flag, but has no pairs or revision with which to correct the stale disclosure. The owner can therefore answer yes to a prompt listing only h1 and create a standing default covering h3. This is a durable consent mismatch caused by an ordinary owner action, so **both ADR-0009 §2.1 conditions hold**. It does not depend on a hostile same-user program impersonating attendance.

**Executed probe:** [setup-snapshot-probe.rs](review-out/setup-snapshot-probe.rs), run by [run-setup-snapshot.py](review-out/run-setup-snapshot.py). The final probe calls the **production** `offer_personal_default`, with a real `Client`, real scratch runtime and real decision/store. A Session wrapper places a successful production `CatalogRequest::UpsertProfile` between the offer's profile read and its Create request. Its capture prompter returns Yes and records every prompt byte. Before the final assertion, the probe verifies that the server created the real default policy including h3 and that the captured disclosure contains h1. It then fails because **h3 is absent from every prompt byte**: **exit 101, 1 failed**. [Final probe log](review-out/setup-snapshot-production-edit.log).

The first probe attempts were fixture failures, not evidence of this finding: an incorrect relative scratch-path lookup; an attempted reuse of an immutable profile revision; and an overlong fixture socket path causing runtime-start timeout. The corrected probe above runs to the intended behavioral assertion. Its typed-input handling is a scripted prompter; the server and catalog edit are real. This is not a second implementation of authority logic.

**Smallest correction:** expose the Create decision's pinned profile revision and concrete scope through its server-built decision view, and render the setup disclosure from that record. Use that same scope for the CLI/TUI Create review. A fresh read of the current profile alone does not establish which snapshot this decision will apply. This is the public consumer for which I-3 allows exposing the stored basis; the contract owner should choose the additive view shape. No fix is retained here.

### M05-W3-R02 — High; blocking: a pause between the default plan and bind still enables a free ordinary alias

**Locations:** [default_activation_m05.rs:559](crates/app/src/operations/default_activation_m05.rs:559), [default_activation_m05.rs:682](crates/app/src/operations/default_activation_m05.rs:682). The ordinary bind deliberately validates as `Activation::Existing`, which ignores pause: [operations.rs:10048](crates/app/src/operations.rs:10048). It then claims the ordinary-alias slots at [operations.rs:10101](crates/app/src/operations.rs:10101).

**Scenario:** default work has an active binding but no ordinary-alias slot—for example its earlier bind did not finish. An identities-triggered activation reads an unpaused plan and chooses `Step::Bind`. The owner's pause commits before the bind begins. `default_bind` calls the general bind path, whose existing-binding semantics permit use during pause, so it materializes the previously free alias and returns `Activated` while the policy is paused. The plan's pause check is not a transactional guard on that slot activation.

The general rule allowing an already active binding to continue during pause is intentional. The bug is using that rule for a **background transition that enables an alias after pause**: ADR-0011 §7.2–§7.3 explicitly refuses background activation under pause, and the wave includes an existing-work/free-slot regression for this promise. The race durably adds slot references and the owner's managed slot files after an ordinary owner pause; it enables previously unavailable ordinary-alias access until the grant ends. **Blocking under ADR-0009 §2.1** for that lasting managed-data/access effect with an owner-action trigger. This is not a claim that pause must revoke an already usable binding.

**Executed probe:** [pause-race-probe.rs](review-out/pause-race-probe.rs), [run-pause-race.py](review-out/run-pause-race.py), [probe log](review-out/pause-race-probe.log). It creates a real managed binding of default work 1 without a slot. Temporary instrumentation at the entrance to `default_bind` commits a **production `PolicyAction::Pause`** before calling the otherwise unchanged bind. This is an explicit scheduling seam, not an unmodified-wire race stress test. The probe verifies that pause is committed, no decision exists, and the binding is still the original one. It fails its free-slot assertion: the outcome is **`Activated`** and the slot is held. **Exit 101, 1 failed.** The instrumentation and test were restored byte for byte. No new remote SSH login was attempted by this probe.

**Smallest correction:** carry an internal background-activation marker/basis into the bind and enforce its pause/default-policy eligibility in the transaction that claims the slot, with the corresponding generation/publication fencing. Keep ordinary foreground Existing-bind behavior. Adding another separate pre-bind plan read alone leaves the same check/write gap. Extend the current existing-work/free-slot test with this interleaving.

## Answers 1–6

### 1. Unattended activation

**New authority:** I found no path in new default-work resolution that unions another profile/workspace policy into personal default scope, changes the recorded lock behavior to satisfy a request, or chooses another environment. `default_policy` requires a personal default containing the endpoint's environment; `plan_in` intersects that policy with the current profile and resolved personal coverage, selects managed pairs, checks automatic-activation permission and checks time/pause/cutoff before starting. The internal stored resolution is personal `Route::CoveredOnly`. `context_m05::on_approval` refuses uncovered work before creating a decision or taking the normal approval/join path. The independently executed covered-only revert proof demonstrated why that carrier is necessary.

The hook's **context activation** may activate an already trusted workspace's covered scope: this is intentional and distinct from its **personal-default warm-up**, which sends the same identities request ordinary ssh sends. An untrusted/ambiguous workspace cannot obtain workspace authority through it. Existing admitted slots/identities remain governed by their pinned grants; listing those is not creation of new default authority. Shared **slot references** can overlap workspace work under the accepted environment-alias model; that is not joining the workspace's authority grant. Ordinary ssh still activates the default's whole covered scope, not a destination-filtered subset (R4).

**Decisions/attendance:** no unattended decision/prompt/Attend/Decide path was found. The live narrowing race left decisions and grants unchanged and returned NotCovered; removing the covered-only safeguard created one decision. CLI hook-uncovered cases run through the actual binary. Workspace and personal grants are separated by the previously reviewed context keys.

**Blocks:** pause/cutoff/policy-stop established before the plan are refused; the eight live default tests passed. My additional virtual-clock/sync probe also returned `Blocked(time_uncertain)` with unchanged operation/grant/decision counts and a free slot (**exit 0, 1 passed**). **R02 is the exception: pause can race the subsequent bind.** Work-stop applies to that work ID; it is distinct from the policy-stop/pause that disables future standing activation.

**Repeated triggering:** already-active work is reused; one flight exists per environment; unsuccessful bases have a 60-second retry interval; blocked/not-covered events are admitted once per policy/kind/reason per hour (in-memory, reset by restart). Successful activations emit once. No extra authority from repeatedly calling identities was found. A same-user program can already use the control endpoint to release/revoke work and cause new work under existing permission; the ability to do that is the documented same-user limit, not a newly demonstrated privilege gain. Rate limiting is not a general OS-resource denial-of-service defense.

**Bound/cancellation:** the signer wraps the complete activation port future in `timeout(2 s)`; the runtime also uses one absolute deadline around its state read and watch wait. Mutex guards do not span awaits in the flight coordinator. Its activation task is owned by the runtime, not the waiter, so a caller timeout does not roll back or cancel it. The live concurrent and timed-out-waiter tests passed and verified the later committed binding/slot and successful subsequent use. These are practical timed tests (the 2-second test allows scheduling slack), not a hard real-time guarantee during executor starvation or synchronous filesystem stalls. No deadlock was observed.
