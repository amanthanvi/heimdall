- **Go (pass):** Observed: Windows now executed; the one Windows defect (argument bytes executed as commands when the target was a .bat/.cmd, 8/16 arguments injected) was a real security defect rooted in CreateProcess running cmd.exe over Go's CommandLineToArgvW quoting; fixed by refusal, independently verified with a mutant. - **Rust (pass):** Observed: the Windows user-data-loss path (request frame written into a regular file named as --socket) and the named-pipe hang are fixed before any write (GetFileType, 001a791); batch arguments delivered exactly with std's escaping. ### Cross-platform integration (25 %): Go 4, Rust 4, confidence medium

**Basis.** Both now run natively on all five spec 3.2 architectures except Windows ARM64, each after one Windows fix round. For Go: a single toolchain cross-compiles every target (observed, X3/X5), purego even builds a working darwin Keychain/Secure-Enclave binary from a Linux container with no SDK (x4/macos, observed exit 0 and ran on the Mac), static-by-default stays true only if CGO_ENABLED=0 is pinned once godbus is linked (x4/linux). Against Go: NCrypt needs hand-bound untyped LazyProc.Call (30 unsafe sites; pointer-lifetime pitfall go vet missed; unverified at runtime), macOS Keychain needs cgo or hand-maintained purego signatures, the darwin wait-status misdecode of SIGSTOP in the standard library (parity-r3c probe 4; x6 section 5 traces it to syscall_bsd.go), .bat/.cmd targets are now refused outright so `run` cannot launch npm-style shims on Windows, go-winio dials at Anonymous level, four inherited dispositions reset by the runtime. For Rust: typed first-party windows-sys for NCrypt/DPAPI/pipes/tokens (compile-verified; pipe part run natively), a safe std client with SECURITY_IDENTIFICATION, std batch-file escaping observed correct 32/32, siginfo available without cgo (which is what let the baseline keep one process group), Iroh cross-compiles under zig for every target (x5). Against Rust: linking macOS frameworks makes darwin builds need a macOS SDK (zigbuild fails; a dlopen variant is untested), zig + cargo-zigbuild required for musl and windows-gnu, cargo-dist cannot do windows-gnu without cargo-xwin, double delivery of terminal Ctrl-C/Ctrl-backslash/resize to the child on macOS in normal use (K6b, ADR section 5), the TUI is killed by an external CTRL_C_EVENT leaving the alternate screen active, exe resolution order differs from PATH.

### Security-sensitive core correctness and maintainability (25 %): Go 4, Rust 4, confidence medium

**Basis.** The two halves of this row point opposite ways and I do not find a full point between them. Correctness and the defects agents leave behind favour Rust: in X2 T1 (exec-equivalent job control, the supervision core) the calibrated review gives Go 3 majors and Rust 0, confirmed by an independent re-run of P1 with its own probe (t1-calibration/verify: 864 records; every Go cell leaves a stopped child with `fg` hanging and nothing but ^C or an external signal recovering it on Linux, every Rust cell recovers with ^Z then fg). The verify README's mechanism analysis says the Rust recovery is inherited from the baseline's shared-process-group design, affordable because siginfo is an ordinary dependency in Rust and not reachable from CGO_ENABLED=0 Go; so this is a stack effect, not implementer skill, which is exactly what a stack decision should count. Also for Rust: the Windows injection defect was Go's (stdlib batch handling that Go can only fix by refusing), while Rust std escapes correctly; language guarantees that matter for protocol parsing and state machines (exhaustive match, must_use, no data races) are observed in the sources X6 cites. Supply chain and maintainability of that core favour Go, and strongly: 17 linked modules vs 77-82 crates, 2 vs 55 unsafe-bearing third-party units (different granularity, Rust is an upper bound), no C runtime vs musl/mingw, govulncheck symbol-level reachability vs lockfile-level cargo-audit, cross-host reproducible vs not, stable fuzzing vs nightly cargo-fuzz, binary SBOM native vs cargo-auditable required (x3). X6 adds that RustSec listed 1 of 20 russh advisories on 2026-10-06, so an agent-maintained Rust SSH product relying on cargo-audit alone would be blind; mitigable by osv-scanner, which is a process fix. Both prototypes have one open major in job control from round 3c (ADR section 6.1) of comparable weight. X4 Linux: go-keyring's plaintext session vs Rust's DH, and Go strings cannot be zeroed, favour Rust on secret handling.

### Release and runtime simplicity (20 %): Go 4, Rust 4, confidence medium

**Basis.** Release favours Go, runtime favours Rust. Release (observed, X3): goreleaser built the full matrix first try with binaries identical to build.sh; two standard flags give reproducibility on one host and across a macOS host and a Linux container; artifact SBOM and vulnerability scan work from the binary with no extra build step. Rust: build.sh needs five remap flags plus linker tricks and a pinned cargo-zigbuild; not reproducible across hosts (zig distribution changes bytes); cargo-dist needed hand fixes, could not build windows-gnu (cargo-xwin missing) and its default profile leaked builder paths; `cargo auditable` is needed for artifact SBOMs; PIE for static musl not reached on stable. Runtime (observed, g02-measurements.json via ADR section 4; X1): Rust artifacts 7x smaller, idle CPU 0.03 percent vs 0.35 percent against a spec 15.1 budget of 0.5 percent, peak RSS 2.3-3.5 MB vs 7.5-8.3 MB, first TUI frame 20 vs 40 ms on native linux-x64 and 32 vs 44 ms on Windows, K17 filter p95 2.7 vs 17.7 ms. None is visible to a user at this slice, but the Go prototype already consumes 70 percent of the idle-CPU budget with a trivial profile viewer and the real product adds pollers and endpoints (inference), and the owner named performance as one of three criteria. Iroh: with it, Rust ships one 4.5-6.8 MB file from the toolchain it already needs; Go ships two files (8.8-11.1 MB), two toolchains, two lockfiles/SBOM/vuln feeds and two signing operations per target (x5 sections 1.5, 4). Without it, the release half alone would read Go 4 / Rust 3.

## 3. Sensitivity

Starting point Rust 3.90, Go 3.70 (Rust +0.20). Single changes that flip or erase the lead: (1) security core Go 4 / Rust 3 (supply-chain-weighted reading of X3): Go 3.70 vs Rust 3.65, Go by 0.05; (2) release/runtime Go 4 / Rust 3 (Iroh deferred, release-only reading): tie at 3.70; (3) agentic row 3/3 (T1 rubric read as implausible and T3 charged to the library): Rust by 0.05; (4) agentic Go 4 / Rust 3 (X6 tooling-weighted): Go by 0.10; (5) ecosystem 3/3 or Go 4 / Rust 3: Rust by 0.15 or 0.10, no flip. Changes that widen the lead: security core Rust 4 / Go 3 (X2 T1 and the batch-injection class weighted): Rust by 0.45; cross-platform Rust 4 / Go 3 (batch refusal and untyped NCrypt as product gaps): Rust by 0.45; release/runtime Go 3 / Rust 4 (Iroh in V1): Rust by 0.40; TUI Go 3 / Rust 4 (rendering correctness weighted): Rust by 0.30. Pairwise: the pro-Go readings (1) and (2) together give Go 3.70 vs Rust 3.45; the pro-Rust readings on security core and release together give Rust 4.35 vs Go 3.45. Robustness: the lead survives any one contestable reading except two, both of which produce a near-tie rather than a Go lead larger than 0.10; every reading that widens it is an observed-evidence reading (X2 calibrated majors, X1b defect class, X5 Iroh cost, T3 rendering). The result is therefore a modest but one-directional lean: no plausible single reading gives Go more than 0.10, while several give Rust 0.30-0.45. Key contestable inputs and my readings: X2 T1 rubric (read as the record does: plausible scenario, ^C and external kill are not normal recovery, so Go majors stand, but counted once, in the 15 percent row); Iroh (read as undecided and scored neutrally in the 20 percent row, with the flip shown); T3 TUI finding (charged to the stack Go+Bubble Tea in the 15 percent row and to Bubble Tea in the 10 percent row; a reader who thinks Go could switch TUI library should move Go to 4 on TUI, which does not flip the result).

## 4. Recommendation: **rust** (confidence: medium)

**Reasons.**
1. On the owner's stated product criteria (maintainability, security, performance), every round-4 experiment that was built to separate the two came out even or in Rust's favour, except X3's supply-chain and release-tooling comparison and X6's tooling half. Rust's advantages are structural (language guarantees, typed platform APIs, siginfo without cgo, std batch escaping, Iroh native, one artifact); Go's are largely process-mitigable (pin a build container, add cargo-deny/vet/auditable and osv-scanner, use build.sh instead of cargo-dist).
1. The controlled in-repo experiment (X2) found that agents left five undetected majors in Go cells and none in Rust cells, from two causes that both sit in the Go stack's design pressure (os/signal without siginfo pushing a separate-process-group model; Bubble Tea v2 inline SGR plus a renderer bug), with equal effort and equal hidden-test outcomes. Independent re-runs confirmed the decisive facts of both causes on byte-identical binaries.
1. Performance headroom under spec 15.1 is an order of magnitude better in Rust (idle CPU 0.03 vs 0.35 percent against a 0.5 percent budget; RSS 3x; TUI latency 5x) and Rust's only material gate risk from the ADR (ring under zig) is closed by X5, while Go's Iroh path is confirmed to be a second language, second toolchain and second artifact.

**Strongest case for the other side.** Go is the smaller and simpler thing to secure and ship: 17 modules against 80 crates, no C runtime in the artifact, zero unsafe in the prototype, govulncheck with reachability, binary SBOMs for free, reproducible across hosts with two flags, goreleaser working first try, a first-party SSH and agent library with thousands of importers, stable fuzzing, 10x faster cold builds for agent iteration, single-toolchain cross builds including SDK-free darwin via purego, once-only terminal signal delivery on macOS, and a TUI that survives external Ctrl-C events. If Iroh is deferred (which spec 3.1 permits) Go's one structural cost disappears, and the X2 defect gap rests on a rubric the record itself calls sensitive and on a TUI library that could in principle be swapped. A supply-chain-first owner could reasonably pick Go.

**Reverse if:**
- G06 records an Iroh deferral or drop for V1 and the owner weights supply-chain surface and release simplicity above agent-left defect rates and runtime headroom: the scored result then becomes a tie or a 0.05 Go lead.
- The X2 T1 rubric is overruled so that a third-party stop of a background job is implausible or ending the job counts as recovery, and the T3 finding is attributed to Bubble Tea with a decision that Go may use a different TUI library: X2 then shows no stack difference.
- Native Windows DPAPI/CNG/TPM runs (X4, currently blocked on owner authorization) show that the Rust windows-sys path fails where Go's hand bindings work, or a native Windows run of the Rust Iroh helper fails where the Go supervisor succeeds.
- crossterm or security-framework become unmaintained with no replacement and the hand-written Rust input/secure-store code proves costlier than X2 suggests, or a Rust dlopen path for macOS frameworks cannot be made to work and the owner requires Linux-hosted darwin release builds.

The post-fix 71/71 results exist only under tests/evidence/artifacts/g02-r4/x1b/{go,rust}/ and the review directories. Either supersede the top-level records or state that the Windows gate pass rests on x1b artifacts, not on the records the plan 6.6 schema was written for.
2. X2 RESULTS.md section 5.3 reports 'one-sided Fisher exact p approximately 0.02' for 5-of-12 vs 0-of-12 and then concedes the cells are not independent. The number should not be in the headline; the honest statement is 'two causes, each observed in 2-3 of 3 Go cells and 0 of 3 Rust cells'. The record's section 6 reading ('real but modest') is fair; section 5.3 overclaims.
3. The T1 calibration (t1-calibration/README.md) got a decisive darwin fact wrong ('^C does nothing; ^\ ends it') because its own driver inherited SIGINT ignored; the independent re-run (verify/) found and corrected it. The classification survived, but P2-P14 of the calibration remain implemented_unverified with the same harness lineage, and only P1 was independently re-measured. The three Go majors rest on P1 alone, so this is acceptable, but the matrix beyond P1 should not be cited as verified.
4. The T1 Go/Rust recovery difference is, per verify/README.md, inherited from the baselines' process-group models and 'nothing in the three Rust cells' T1 changes is exercised by the P1 recovery, so no credit for it belongs to those changes.' 5. T3 N1 is counted against Go in the 15 percent row and bears on the 10 percent row; the two rows are not independent and a re-scorer could double-count. I have charged the agentic row with the undetected-defect fact and the TUI row with the library's rendering correctness, and said so. 'Ring under zig is closed' is closed for building only.

## 6. Questions for the owner (beyond D1)

1. Iroh in V1: is G06 expected to ship an Iroh reference flow in V1 (spec 3.1 target), or is the transport-specific deferral the working plan? This decides the 20 percent and 5 percent rows and is the single largest lever on the result.
2. Windows batch targets: is a product that refuses to launch .bat/.cmd files (npm, npx, yarn shims on Windows) acceptable, or must `run` launch them safely? If the latter, Go needs a custom cmd.exe quoting layer that its standard library deliberately does not provide.
3. X2 T1 rubric: do you accept that a third-party stop of a background job is a plausible interactive scenario and that ^C or an external `kill` is not a normal recovery? Your answer decides whether the three Go T1 majors stand.
4. TUI library binding: is the choice 'Go + Bubble Tea' and 'Rust + Ratatui' as the plan names them, or may the chosen language pick another TUI library later? If the latter, the T3 finding weighs on the library, not the language.
5. Supply-chain policy: for a Rust product, do you accept as mandatory process a pinned build container (cross-host reproducibility), cargo-deny + cargo-vet + cargo-auditable, and an OSV/GHSA scanner in addition to cargo-audit? For a Go product, do you accept a pinned CGO_ENABLED=0 release recipe and a goreleaser archive-reproducibility configuration that was not tested?
6. Windows closure: authorize DPAPI/CNG/TPM runs on the owner PC (or a disposable account or host) and a second non-admin account, so the untyped Go NCrypt bindings and the other-user DACL claims can be executed; these are language-neutral blockers that also gate G03/G04.
7. macOS release shape: will darwin artifacts be built and signed on a macOS runner regardless (Developer ID, notarization), making purego's SDK-free Linux cross-build moot, or do you need Linux-hosted darwin builds?
8. Record hygiene: should tests/evidence/g02-{go,rust}-x1-windows.json be superseded by post-X1b records so that the Windows gate pass is carried by schema-conformant evidence records rather than by artifact directories?

## Summary

Hard gates: Go and Rust both pass child/IPC correctness (under the D3 rulings), Windows/WSL viability, no unsupported security assumption, practical distribution, licensing and the shared domain; maintained dependencies stays a judgment for both (Go: untagged ultraviolet with an observed renderer bug; Rust: crossterm stalled 18 months, security-framework seeking a maintainer). Round 4 moved four gates from uncertain to pass for both candidates by native Windows and linux-x64 execution, each after one independently reviewed Windows fix round. Weighted totals: Rust 3.90, Go 3.70. The lead comes from the redefined agentic/open-source maintainability row (X2: equal effort and hidden-test outcomes, but five calibrated majors left undetected in Go cells vs none in Rust, from two stack-rooted causes) and the ecosystem row (Iroh native; typed platform APIs), with cross-platform, security core and release/runtime scored even because each has one half favouring each side (Rust: correctness, guarantees, batch safety, performance headroom, one artifact with Iroh; Go: 5x smaller supply chain, no C runtime, reproducible cross-host, simpler release tooling, first-party SSH libraries). Recommendation: Rust + Ratatui, medium confidence. The result is a modest lean that survives every single contestable reading except a supply-chain-first security-core reading or an Iroh-deferred release-first reading, each of which gives a tie or Go by 0.05; the readings that widen it are the observed ones. Main evidence concerns: the top-level x1-windows records still say fail; the X2 Fisher p-value overclaims; the T1 split rests on P1 and a rubric; T3 bears on two rows; X3 counts are not like-for-like; Iroh was never run on Windows; Go's gate pass removed a capability (batch shims) that the gate table does not surface.
