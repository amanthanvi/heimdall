# M08 W0 independent review: candidate `064134a3` (`m08/w0`), range `2785d6ea..064134a3`

Reviewer: one independent review under ADR-0009 §2.1. Worktree read-only. Probes and fixtures lived only in this directory and were removed after this report was written (the report is the only file left).

## Verdict: MERGE-AFTER-FIXES

Nothing found blocks under ADR-0009 §2.1 read strictly: none has a lasting effect on remote trust or the owner's data, and none needs more than an ordinary I/O error or a hostile same-user program. One moderate finding (R01) is a one-line fix in `install.sh` that I recommend before merge, because it makes the update path claim a rollback target that does not exist. The rest are low and can be recorded as residuals or fixed in the same sweep.

The support-bundle redaction (the main security surface) held against everything I tried in its default mode. Its one real gap (R05) is in `--include-identifiers` mode only.

## Findings

Severity per ADR-0009 §2.1: blocking / moderate / low.

### M08-W0-R01 (moderate): `install.sh` step 3 hides a failed backup of the current executable, then replaces it and says the previous one is kept
- `tools/packaging/install.sh:110-112`:
  ```
  if ! ln -f -- "$cur" "$prev" 2>/dev/null; then
      cp -p -- "$cur" "$prev.tmp" && mv -f -- "$prev.tmp" "$prev"
  fi
  ```
  Under `set -e`, a failing `cp` in a `&&` list that is not the final command does not exit the script.
- **Scenario:** the filesystem refuses the hard link (FAT/exFAT, some network or overlay mounts) and the copy fails (disk full, I/O error). Step 4 still runs, so v2 is replaced by v3 and nothing keeps v2. `heimdall.previous` is left as whatever was there before (v1) or is absent. The script exits 0 and prints "the previous executable is kept as …/heimdall.previous (./install.sh --rollback puts it back)". A later `--rollback` then silently installs v1, two versions back.
- **Reproduced:** yes. A fake archive pair, PATH shims that make `ln` fail and `cp` fail for `*.tmp`, prefix holding cur=2.0 and prev=1.0, then install of 3.0. Output: `cp: simulated ENOSPC`, then "installed …", then "previous executable is kept as …". Result: cur=3.0, prev=1.0, exit 0.
- **Impact limit:** the user's state is untouched. An older build refuses a newer store and changes nothing (the journey's H4 observation), so the harm is a lost rollback target plus a false message.
- **Fix:** `cp -p … && mv -f … || { rm -f -- "$prev.tmp" "$new"; die "could not keep the previous executable; nothing was changed"; }`.
- **Test gap behind it:** plan U2a asks for "a kill and a full-disk error after each of the four steps". `install-selftest.sh` only uses `HM_INSTALL_TEST_STOP_AFTER`, a clean exit after a step. It never injects a failing `cp` or `ln`.

### M08-W0-R02 (low): a dangling `.heimdall.new` symlink makes the install write through it, and the symlink becomes the installed `heimdall`
- `install.sh:85` removes a leftover only when `[ -f "$new" ]`, which is false for a dangling symlink. `install.sh:98` (`cp -- "$here/heimdall" "$new"`) then writes through the link. Step 2's digest check follows the link and passes. Step 4's `mv -f` moves the symlink itself to `$cur`.
- **Reproduced:** yes. With `p2/.heimdall.new -> /tmp/…/victim` (not present before), the install exited 0, created `victim` (an executable copy of the archive's `heimdall`), and left `p2/heimdall -> …/victim`.
- **Why low:** it needs write access to the prefix directory. The default `~/.local/bin` is the user's own, so that is a hostile same-user program (ADR-0009 §2.1, residual). It matters only for a shared or world-writable `--prefix`, which the script does not prohibit.
- **Fix:** test `[ -e "$new" ] || [ -L "$new" ]` before the `rm -f`, or always `rm -f -- "$new"`. Optionally refuse a symlinked `$cur` or `$prev`.

### M08-W0-R03 (low): a `MANIFEST.sha256` without a trailing newline leaves its last entry unchecked
- `install.sh:75`: `while IFS= read -r line … done <"$here/MANIFEST.sha256"` skips an unterminated final line.
- **Reproduced:** yes. A manifest of `heimdall` and `README` with no final newline and a tampered README installed with exit 0.
- **No effect on what gets installed:** the executable is re-checked later against `want_exe` (a `grep`, which does read the last line), and nothing else is copied. Real manifests end with a newline (`provenance.py write_manifest`). Fix: `|| [ -n "$line" ]` in the loop condition.

### M08-W0-R04 (low, inference from code): the "a runtime is running" guard fails open
- `install.sh:50-53` greps the installed binary's `service status` output for `"running":true`. `crates/heimdall/src/service_cmd.rs:~452-466` prints that only when the runtime answers a hello. When an advertised runtime is up but unreachable (starting, wedged), `connect` fails and the envelope has no `"running":true`, so `running()` returns false and the update proceeds.
- Not reproduced: it needs a real runtime, and a release binary may not run on this host. The journey's step `a31_update_is_refused_while_the_runtime_runs` covers only the healthy case.
- The check is also TOCTOU by nature. Nothing is corrupted on POSIX (the running process keeps its inode). The cost is an older runtime with a newer store, which refuses safely.

### M08-W0-R05 (low): `--include-identifiers` still writes invisible and formatting characters the docs say are refused
- `crates/support/src/screen.rs:361-373` `has_control` blocks C0 and C1, U+2028/9, U+200B-200F, U+202A-202E, U+2060-2064, U+2066-2069 and U+FEFF. The module doc (`screen.rs` header) says "no invisible or bidirectional formatting character".
- **Not blocked, reproduced with `screen_identifier`:** the Unicode tag block U+E0000-E007F, U+061C (Arabic letter mark), U+206A-206F, U+2065, variation selectors (U+FE0F), U+00AD, U+034F, U+3164, U+180E.
- **End to end:** `build()` with `include_identifiers: true` and a host `"build-host" + tag-encoded "SECRET"` wrote the tag characters into `bundle.bytes()`. They are invisible in the preview, which is the "preview is the bundle" promise. Default mode is unaffected: the value goes only to the inverse map, and the bundle held none of it.
- **Why low:** it needs the user to pass `--include-identifiers` and an identifier whose text an outsider controls (a key comment or a hostname). The invisible payload would then ride along to whoever reads the bundle, human or tool.
- **Fix:** reject `char::is_control` plus the Unicode `Cf` and `Cc` categories, the tag block and the variation selectors in `has_control` (or restrict included identifiers to printable ASCII and graphic Unicode).

### M08-W0-R06 (low): `verify_artifact.py`'s generic home-path rule is narrower than its docs, so a standalone run passes a bare home path
- `verify_artifact.py:54-55` matches a home path only when it is followed by one of `.cargo|.rustup|.t3|GitRepos|src|code|work|dev|projects`. The docstring and `tools/packaging/README.md` say "no build-host path (a home directory …)".
- **Reproduced:** with no `--forbid`, an executable containing `/Users/bob/Desktop/x`, `/home/bob/.local/share/x` or `C:\Users\bob\AppData\Local` passes.
- In `build-release.sh` the builder's own `$HOME`, checkout, cargo and rustup paths and user name are also passed as `--forbid`, so those are caught. What the standalone verifier misses is any other host's home path, for example one baked into a precompiled or vendored blob.
- **Fix:** either widen the rule to `(/Users|/home)/[^/]+/` and `[A-Za-z]:\\Users\\[^\\]+\\` (allowlisting `/home/builder`-style remapped prefixes), or say in the docs that the generic rule is a tripwire and the forbid list is the control.

### M08-W0-R07 (low): scan-coverage gaps in `verify_artifact.py`
All reproduced against the module's `verify()` with fixtures.
- **`--allow-exact` can hide an overlapping forbidden text.** The mask is applied to bytes before the forbid scan (`:363`). Allow `builderx.label.` and forbid `/Users/builderx`, with data `/Users/builderx.label.suffix`: PASS. The documented scope ("the same text anywhere else still fails") holds only for non-overlapping occurrences. With the real label (`io.github.amanthanvi.heimdall.`) and the real forbid list I could not construct a realistic hide, so this is theoretical today.
- **UTF-16 is not scanned.** The same forbidden text or a full canary in UTF-16LE passes. This matters only for the Windows archive (wide-string constants), which has never been built.
- **Archive metadata is not scanned.** A tar whose members have `uname`/`gname` equal to the builder name and a PAX header with a home path passes. `provenance.pack()` zeroes them (checked: uid/gid 0, empty names, no PAX, gzip flags 0), so today's archives are clean. The verifier would not catch a regression in `pack()` or an archive built elsewhere.
- **An empty `--forbid` value is silently dropped** (`:353`, `if t`). `build-release.sh` filters entries under 4 characters (`awk 'length($0) >= 4'`), so a short `id -un` is silently not forbidden. Neither is stated in the README.
- **A canary is detected only as `HEIMDALL_CANARY_(KIND_)*<8+ lowercase hex>`.** Other shapes pass (lowercase prefix, uppercase hex, fewer than 8 hex digits). The shape matches `testkit::canary_comment`. I mention it only because AGENTS.md treats any `HEIMDALL_CANARY_*` in output as a defect.

### M08-W0-R08 (low): the soak and lane scripts have no container or `HEIMDALL_TEST_*` guard of their own, and the journey kills by name
- Only `journey.sh --build release` has the refusal logic, which I ran (below). `tools/benchmarks/m08/entry.sh` (runs `install -m 0755 … /usr/local/bin`, `chown`, `runuser`), `lane.sh` and `workload.py` assume the container that `run-soak.sh` creates. Run by hand on a Linux host as root (the devbox), `entry.sh` would write `/usr/local/bin` and start sshd and agents. Nothing in the range does that, and `lane.sh` fails on a host without `/src`.
- `journey.sh:178` `kill -9 "$(pgrep -u … -x heimdall | head -1)"`, and the roll-forward loop that kills every `pgrep -x heimdall` for the uid, are by-name kills. AGENTS.md and the global rules say never kill by name pattern. They are confined to the container's disposable account and the journey refuses to start elsewhere, so I rate this low. `workload.py` is better: it checks uid and `comm` against the PID the runtime advertised.
- **Fix:** a shared `in_container` refusal at the top of `entry.sh` and `lane.sh`. For the journey, record the runtime PID from `service status` and verify uid and `comm`, as `workload.py` does.

### M08-W0-R09 (low): test-coverage gaps against the claims they carry
- `install-selftest.sh` has no failing-`ln`/`cp` case (see R01) and no symlink or pre-existing `.heimdall.new` case. It does not run `--rollback` interrupted mid-way. In that case the rerun's first line, `rm -f -- "$new" "$tmp"`, deletes the spare copy of the executable the rollback had replaced, so the newer one is lost. Low: archives are reproducible.
- `journey.sh:112` `a31_install_edits_no_shell_profile` greps only `~/.bashrc` and `~/.profile`. `~/.ssh` is created after install (`journey.sh:128`), so the journey cannot see whether install touched it. The claim "never edits PATH, profiles or `~/.ssh`" is true by reading `install.sh` (it contains no write to any of them). It is not tested.
- `deny-selftest.sh` has no case showing the `webpki-roots` exception is narrow. I checked that by hand (below) and it is.
- `examples/reference-config/check.py` lists `format` as known but does not enforce it. Two `format` uses in `config.schema.json` pass unchecked. Nit.

## What I checked and found clean (observed unless marked)

**Support bundle (`crates/support`)**
- `cargo test -p heimdall-support`: 10 unit and 14 adversarial tests passed.
- Read `bundle.rs`, `screen.rs`, `value.rs`, `input.rs` in full. There is no bare `String` input. `Secret::new` and `FreeText::new` drop their argument. `Ident` and the string-valued types `Debug`-print kind and length only or a withheld marker. The inverse map is in neither `bytes()` nor `preview()`, which my probe confirmed for the default-mode host. Every identifier is screened before pseudonymization, so a failing value reaches neither the bundle nor the inverse map.
- Withheld-count keys are static or screened code-shaped field names. Field names are `&'static str` and code-screened with a 40-byte cap. The bundle size is checked against 8 MiB, and an overrun is an error, not a truncation.
- Adversarial identifier probes with `screen_identifier` (observed):
  - Rejected: canary with ZWSP, tag or variation selector inside, canary in any casing or spacing, armor with spaces or Unicode dashes (`BEGIN EC PRIVATE KEY`, `Begin DSA`, `B E G I N RSA`), 32+ hex runs, a 31-hex run split by a dash, a base64 key split by a dot, a PEM body line, an `ssh-ed25519` public line, NUL and C1 characters, over-length values.
  - Accepted by design, and documented as unrecognizable: word-like secrets (`correcthorsebatterystaple`), base64 in short space-separated chunks, a Windows home path (only in include mode, with a preview). `H3IMDALL_CANARY` is not the canary.
- A `Code` is `[A-Za-z][A-Za-z0-9._:-]*` up to 64 bytes, so a code-shaped host or user name would be exported if a caller passes data as a code. The plan already assigns that to U6b ("codes come only from enumerations", with a source-check test). Not testable in W0.

**`install.sh`**
- It never edits PATH, a shell profile or `~/.ssh` (the only PATH text is an `echo` of a line for the user to add). Prefix as a symlink, a prefix with spaces, a symlinked or pre-existing `heimdall.previous` (the victim file was untouched, because `ln -f` unlinks the symlink), and interrupted update reruns behaved safely.
- `install-selftest.sh`: PASS, 18 checks.
- **The trust model is stated honestly.** The script header and `install.md` §1 both say the archive must be checked against the repository's `SHA256SUMS` first, that a replaced archive carries a replaced script, and that `MANIFEST.sha256` only catches damaged or partial extraction. `shasum -a 256 -c SHA256SUMS --ignore-missing` works on macOS shasum 6.04, and it fails with "no file was verified" when the archive name is not listed.

**`verify_artifact.py` and `provenance.py`**
- `verify_artifact.py --self-test` (23 cases) and `provenance.py self-test` pass. The generic rules scan real bytes, and `--allow-exact` masks only the `--forbid` scan (the generic-rule self-test case confirms it). Tar members must be regular files or directories and are checked for `..`, absolute names and drive letters. Zip links are rejected. Unparseable executables fail closed. `pack()` is deterministic (two packs byte-identical) with no owner names, no PAX headers and no gzip name. The index lists only regular, non-symlink files and never itself.

**`deny.toml` and `deny-selftest.sh`**
- `cargo-deny 0.22.0` with `check licenses sources bans`:
  - The root workspace passes, and so does `crates/heimdall --features iroh`, both with exit 0. cargo-deny warns about an unused licence allowance ("ISC unmatched").
  - The exception is no broader than ADR-0014 §4.6. In a scratch fixture a crate named `webpki-roots` under CDLA-Permissive-2.0 passes, and any other crate under CDLA-Permissive-2.0 is rejected ("license is not explicitly allowed").
  - `[sources]` denies unknown registries and git. `allow-git` is empty.
- Advisories are deliberately outside it (plan §U4a; M06's audit gate). That matches the plan. I did not review `audit_gate.py`.
- One limit: `[licenses.private] ignore = true` also ignores the licence of a publish-less workspace path crate. That is the recorded design (workspace crates are `UNLICENSED` pending B17), but it is not limited to the workspace's own crates.

**Journey driver and soak harness**
- Ran `journey.sh` (no heimdall started, no container; its exit was 2 each time):
  - `--build release` outside a container: refused ("no container was detected").
  - `--build release` with a preset `HEIMDALL_TEST_SECRET_STORE`, and with `HEIMDALL_TEST_FOO=`: refused.
  - `--build debug`: sets `HOME`, `HEIMDALL_HOME`, `HEIMDALL_TEST_SSH_HOME`, `HEIMDALL_TEST_SECRET_STORE=scratch`, `HEIMDALL_TEST_MGMT_STORE=fixture-file:…` and `HEIMDALL_TEST_IROH_KEY_STORE` under one `mktemp -d` root, checks they sit inside it, prints "the debug journey is not implemented yet" and removes the scratch. The debug journey itself does not exist, so nothing debug-side starts. The comment in `journey.sh` says "six variables verified"; the loop checks the five path variables plus the secret-store value.
  - `--build` omitted: refused. `run-journey.sh` with bad arguments: refused.
- `in_container` is a heuristic: `/.dockerenv`, `/run/.containerenv`, or a cgroup match. Creating the first two needs root. On this Mac `/proc` does not exist and the check refuses.
- Read `run-journey.sh` and `run-soak.sh`: the containers use `--network none --cpus 2 --memory 2g --pids-limit 512 --init`, with the repository and archives mounted read-only. No path reaches the owner's `~/.ssh`, keychain or credential store from these scripts (the journey writes only the container account's own `~/.ssh`).
- `workload.py` kills only the PID it started, or the runtime PID after checking uid and `comm`. `analyze.py --self-test`: 9 cases pass.

**Other**
