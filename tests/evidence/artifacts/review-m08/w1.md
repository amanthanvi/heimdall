## Verdict: MERGE

**No finding blocks under ADR-0009 §2.1.** A finding blocks only if both hold: (1) it has a lasting effect on remote trust, recovery records or the owner's data, or it bypasses consent; (2) its trigger is one Heimdall must withstand. None of the findings below meets the first condition:

- **The installers** delete nothing that is not their own. Their gaps produce a refusal, a misleading message, or a helper of the wrong version, which the hello refuses (ADR-0014 §3.5).
- **The fuzz items** concern the record. No finding is hidden, and the seven "met" claims follow from the raw data.
- **`crates/stategen` is provisional and has no dependents** at `7b9c7533`. `crate_graph.py` reports `heimdall-stategen -> (none)`, and `git grep` finds no user outside the crate and its test. So no product path reaches R01–R03 yet. Even once the crate is wired in, their effect is a refusal (`state_corrupt`) or a misclassified residue generation, and the pointer still decides what is served.

**Fix before U2b wires the crate in:** R01 (moderate), with a regression test.

## Findings

### M08-W1-R01 (moderate): `abandon()` removes the staging intent even when removing the staged generation failed, leaving an orphan nothing will remove

- **Where:** `crates/stategen/src/generations.rs:602-615` (`abandon`). It is called from `publish` (`:401`) and from `stage_and_switch` (`:467`).
- **What the code does:**
  - `let _ = self.discard_staged(name)` ignores the error.
  - It then removes the intent (install, restore, reset), or rewrites it as pending (adopt). The intent is the only evidence that the directory is a leftover.
  - The next start-up treats a directory that no intent names as a real generation (`a_directory_no_intent_names_is_never_removed`).
- **Scenario 1 (install):**
  1. A first install's staging fails. This can be the caller's SQLite copy failing (for example, disk full), or any staging I/O error.
  2. The cleanup's `remove_dir_all` then fails too. On Windows a file held open by antivirus or the indexer is enough.
  3. The pointer was never written, yet the next `open()` returns `state_corrupt` (`PointerMissing`): there is no intent, and `generations/` is not empty.
  4. Every operation is then refused, and recovery is deferred to U0. This contradicts the 2026-11-23 ruling, under which a first publication whose pointer was never written is discarded and run again.
- **Scenario 2 (restore):**
  1. A restore's `GenerationDirSync` fails after the record is written and synced, and the cleanup fails.
  2. Start-up serves `g-a` and removes nothing.
  3. `residue()` lists `g-b` with a complete record `(Restore, epoch 1, from g-a)`, so it is indistinguishable from a completed earlier restore.
  4. This contradicts ADR-0014 §3.6: "the record is what distinguishes … a completed restore … from a staged generation that never became current". It also contradicts §3.4: start-up removes a staged generation that never became current.
- **Reproduced:** yes, with a two-fault `Fs` wrapper around `RealFs`, run as a temporary example in the worktree (`probes/stategen_probe.rs`, output in `probes/stategen_probe.txt`):
  - P1: `publish → Err(Caller("copy failed"))`, then `intent=false staged=true`, then the next open is `Err(Corrupt(PointerMissing))`.
  - P2: `publish → Err(Io GenerationDirSync)`, then the next open serves `g-a` with `removed_staged None`, and `residue: g-b record=Some((Restore, 1, Some("g-a")))`.
- **Why the fault set misses it:** it injects exactly one fault, so the cleanup itself never fails.
- **Smallest fix I would accept:** in `abandon`, return early, keeping the intent and the temporaries, when `discard_staged` fails. A pending or switching intent naming a generation the pointer does not name is already discarded by the next start-up.
- **Regression test:** the caller's `populate` returns `Err`, with a `FaultFs` fault at `Point::Cleanup` nth 0. For an install, the next open is `FirstPublicationPending`. For a restore, it serves `g-a` with `removed_staged == Some(g-b)`.

### M08-W1-R02 (low): an empty `generations/` left by a failed first install, plus any stray entry in it, is `state_corrupt`

- **Where:** `crates/stategen/src/generations.rs:341-344` and `:701-708`. `generation_names` counts every entry, not just generation directories. `stage()` creates `generations/` (`:517-523`) and nothing removes it.
- **Scenario:**
  1. A first install fails cleanly at any step after `GenerationCreate`, for example `RecordSync`. Start-up afterwards is `Empty`, as intended.
  2. Then any entry appears in `generations/`, such as `.DS_Store` from Finder or an editor's backup file.
  3. Start-up is now `state_corrupt` (`PointerMissing`) and a new install is refused, with no recovery until U0.
- **Reproduced:** yes, P3 in `probes/stategen_probe.txt`: `open with generations/.DS_Store: Err(Corrupt(PointerMissing))`, and `a new install: Err(...PointerMissing)`.
- **Fix:** count only entries that are directories and parse as a `GenerationName`. That does not select a generation, so it keeps to the ruling. Alternatively, have `abandon` remove a `generations/` it created and left empty.

### M08-W1-R03 (low): a full-length but invalid last ledger record makes the ledger permanently "damaged"

- **Where:** `crates/stategen/src/ledger.rs`.
  - `read` (`:143-154`) treats only a short tail as torn.
  - `append` (`:159-170`) only realigns, and keeps appending after a bad record.
  - `trim` (`:187-188`) refuses a damaged ledger.
- **Scenario:**
  1. A crash during an append, before its sync, leaves the file extended to a full 48 bytes of zeros. Some file systems do this after power loss or a kernel crash.
  2. The request never proceeded, so this is semantically a torn tail. Instead, `read()` returns `Damaged(n)` from then on, every later append succeeds behind it, and `trim` refuses for ever.
  3. A restore then treats the ledger as unreadable. The epoch fence still holds, but precise answers to retries are lost.
  4. The ledger can never be trimmed, so it grows until `READ_LIMIT`. Past that, `append` fails and every mutating request is refused, which is years away at realistic rates.
- **Reproduced:** yes (`probes/ledger_probe.rs` and `.txt`): `Damaged(2)` after a zero-filled third record, the next append `Ok`, `read` still `Damaged(2)`, `trim` `Damaged(2)`.
- **Limit:** the trigger is in the power-loss class, which the crate states is not established. So this is low.
- **Fix:** let `append` cut a final record that does not decode, as it cuts a short tail (only the last record, and only before appending). Or have `read` report such a final record as `torn_tail`.

### M08-W1-R04 (low): `install.ps1`'s "finish an interrupted update" step decides from file presence alone

- **Where:** `tools/packaging/install.ps1:368-371`. The condition is: no current executable, a `.previous` executable, a current helper, and no `.previous` helper. It is evaluated after the leftover cleanup at `:345-346` has already removed the staged pair, which is the one sign of an interrupted run.
- **Scenario:**
  1. The current executable is lost: deleted, or quarantined by antivirus, which is plausible for an unsigned executable.
  2. At the same time, `.previous` holds an executable without its helper. That can come from an older archive without a helper, or from a step-3 run that discarded the older `.previous` helper and then failed to delete `heimdall.previous.exe`.
  3. A rerun then moves the current version's helper beside the older executable and prints "finished an interrupted update", although nothing was interrupted.
  4. `-Rollback`'s names-only check passes, and the rollback installs older executable + newer helper with exit 0.
- **Reproduced:** yes, with fake archives under pwsh 7.7.0 on macOS (`probes/probe-install.ps1`, case A). This is a logic rehearsal, not Windows evidence. The final state was `cur=exe 1-nohelper curH=helper 2`, rollback exit 0.
- **Effect:** a helper of the wrong version, which the hello refuses. Nothing is deleted.
- **Fix:** evaluate the condition before the leftover cleanup, and require the interrupted run's staged files (`.heimdall.new.exe` present), or a marker file written before rename `3a` and removed after `4b`.

### M08-W1-R05 (low): two stated installer guarantees are wider than the code

- **(a) A repair whose last rename fails does not put the helper back.**
  - **Where:** `install.ps1:426-437`, and the header at `:39`, "A failure part-way puts BOTH halves back".
  - **What happens:** in repair mode `Remove-OwnedHelper $curH` deletes the old helper before `4b`. When `4b` fails, `Undo-Recorded` has nothing to undo, and the script still says "the update failed and was undone, executable and helper together". The install is left with no helper. The old helper was damaged or different, so no real data is lost, and a rerun repairs it.
  - **Reproduced:** probe case B, `HM_INSTALL_TEST_FAIL_AT=4b`, giving `curH=<absent>` and the "undone" message.
- **(b) A stop between renames `3a` and `3b` does not leave the previous pair under its `.previous` names.**
  - **Where:** `docs/operations/update-and-rollback.md:31-34` and `install.ps1:45-47` say it does.
  - **What happens:** at that point the old helper is still at the current name. `-Rollback` refuses ("missing linux-x86_64.previous") with no `heimdall.exe` in place. Rerunning the new archive's script completes the update correctly.
  - **Reproduced:** probe case C.
- **Nit:** `-Rollback` "refuses, and changes nothing" (`update-and-rollback.md:53-57`), but `Settle-InterruptedRollback` (`install.ps1:277`) may move files before the refusal.
- **Fix:** correct the wording, or have the repair rename the old helper aside and put it back on failure. In the refusal message, also name the simpler recovery: rerun the new archive's `install.ps1`.

### M08-W1-R06 (low; W0 code, unchanged in W1): the live-process check compares a non-canonical path string

- **Where:** `install.ps1:61-64` (`$Prefix` is used as given) and `:216-223` (`$p.Path -ieq $cur`).
- **What happens:** with a relative `-Prefix`, or one that passes through a link, an update goes ahead while a process started from the install path is running and `service status` says "none" (the R04 case the check exists for).
- **Reproduced on macOS:** a small compiled stand-in ran as `heimdall.exe` with `HM_INSTALL_TEST_STATUS=@none` (`probes/probe-live.txt`):
  - canonical prefix: refused, "a process started from … is running";
  - relative prefix: exit 0, installed;
  - prefix through the `/tmp` symlink: exit 0, installed.
- **On Windows (inference):** the same would follow from forward slashes, a junction, a `subst` drive or an 8.3 short name.
- **Fix:** `$Prefix = [System.IO.Path]::GetFullPath($Prefix)` before use, and state the link or short-name limit.

### M08-W1-R07 (low; pre-existing line, edited in W1): step 2 checks only the staged executable's digest

- **Where:** `install.ps1:413`.
- **What happens:** ADR-0014 §4.3 step 2 checks "their digests". The staged helper files are copied at `:404-409` and never re-hashed before rename `4b`. A copy that differs is put in place and reported as installed: an I/O fault, or the unpacked tree changed after step 0. The next run's `Helper-Ok` would detect and repair it.
- **Source:** derived from the code; not reproduced.
- **Fix:** hash each staged helper file against `$wantHelper` before step 3.

### M08-W1-R08 (low): fuzz stopping-rule records

All data was read from the campaign volume `hm-m08-fuzz` through a read-only container: `results.txt`, the per-target logs, and the artifact directories. Nothing was run or changed.

- **(a) The cumulative time mixes product trees.**
  - **Where:** `fuzz/run-campaign.sh:154` sums every exit-0 run in `results.txt` whatever tree it ran on. The runs do not record their tree.
  - **The data:** 3,900 s of `sshconf_parse`, `gitedit_scan`, `control_frame` and `project_manifest` ran before the merge (`bd1a8c43`). The merge changed `crates/sshconf` (4 files) and `crates/ipc/src/session.rs`.
  - **The forward risk:** `fuzz/README.md:113-117` plans make-ups that rely on that time. After the planned 3,300 s + 1,800 s, `control_frame` would show 10,800 s but have only 6,900 s on current code, and the column could then say `met`. ADR-0014 §2.3's own rerun rule says a campaign on a changed crate does not stand.
  - **The seven "met" claims are not affected:** with pre-merge time excluded, each has at least 7,800 s on current code.
- **(b) "No new coverage" was narrowed to edges without a recorded ruling.** The earlier row (`fuzz/README.md:62`) used "a new or reduced input". The closing table records `ft` only at the end. In fact:
  - `registry_hm1` added 24 inputs in its closing run (ft 1511 → 1549);
  - `runtime_instance` added 4 (ft 5224 → 5231);
  - `known_hosts_match` and `registry_line` each gained 1 ft.

  `fuzz/README.md:111` says "by a few". Reading `cov` matches libFuzzer's own term, but the orchestrator should rule on it, and the record should show ft at load → end.
- **(c) Six runs exited 1 and no record mentions them.** On 2026-11-22 from 12:08 to 12:21 UTC, 300 s each: `frame_codec`, `sshconf_eval`, `registry_line`, `issuer_protocol`, `issuer_backup`, `known_hosts_match`.
  - Every artifact directory is empty now and the logs have been overwritten, so the cause cannot be recovered.
  - *Inference:* probably failed builds rather than crashes. But `cargo fuzz run` also exits 1 on a crash, so the record should say what they were.
- **(d) The evidence will not survive cleanup.** The closing-pass logs (INITED and DONE lines) and `results.txt` exist only in the volume that `run-campaign.sh clean` removes. Nothing is preserved under `tests/evidence/artifacts/` (AGENTS.md "Evidence discipline").
- **(e) Wall-clock time is labelled CPU-hours.** `secs` is the requested `-max_total_time` in wall seconds, but `fuzz/README.md:17` speaks of CPU-hours. That is defensible (one process per CPU, 2 at a time), but it should be stated.
- **Fix:** record the commit (or a build ID) per run in `results.txt` and sum per build; ft at load → end in the table; a line for the six exit-1 runs; a copy of `results.txt` and the closing-run log tails under `tests/evidence/artifacts/`.
