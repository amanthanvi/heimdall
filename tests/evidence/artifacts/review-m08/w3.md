## W3-R01: the adoption can lose the bridge's owner-only downgrade write (blocking, narrow)

**Where:**
- `crates/store/src/ext_runner.rs:447-494` (`bridge_record_with`). It calls `check_version` at
  `:461`, **outside** the `BEGIN IMMEDIATE` transaction that writes at `:482-493`. Nothing
  inside that transaction checks the fence again.
- `crates/store/src/layout.rs:378` (`fence`), `:410-426` (`copy_fenced`, `VACUUM INTO`) and
  `:124` (`locate` answers `Flat` while an adoption is unfinished).
- `crates/runtime/src/paired.rs:446` (`state_db_of_home` follows `locate`).
- `crates/heimdall/src/m06_cmd.rs:5043`: the marker is written only when the record **fails**.

**The contract it breaks:**
- **ADR-0012 §3.2:** the bridge is "the one exception to the single-writer rule". It writes
  the downgrade row without the instance lock. The row stands until the attended lift, and if
  the write fails, a fail-closed marker is queued.
- **ADR-0014 §3.6 adoption:** the order (intent, fence, copy, publication) assumes that,
  under the instance lock, nothing writes the flat family after the fence. The bridge is
  outside that lock.

**The failing scenario.** A runner home from a pre-generation build is updated to this build.
The owner starts the runtime, which adopts the flat store under its lock. At the same time, a
session under a paired client's key arrives with a pty or a forwarded agent. Heimdall's own
management `ssh` passes `-T` and `ForwardAgent=no` (`crates/app/src/remote_env_ssh.rs:185`,
`:221`), so this is another tool using that key, or a person. `remote serve` refuses the
session and records the runner owner-only (`refuse_session`), in this order:

1. The bridge resolves `<state>/state.db`, because no pointer exists yet.
2. The bridge's `check_version` reads `user_version`: still 14, unfenced.
3. The runtime's `fence()` commits `user_version = 2_000_000_000`. If the bridge reached
   `BEGIN IMMEDIATE` during that transaction, it waits on its busy timeout.
4. `copy_fenced` opens the family and starts `VACUUM INTO`. Its read snapshot does not hold
   the bridge's row.
5. The bridge takes the write lock and commits `runner_owner_only` into the **fenced** flat
   family. The write succeeds, so no `runner-downgrade-unrecorded` marker is written.
6. The pointer switch publishes the copy. The row is only in the residue flat family, which is
   never served again.

**The outcome:**
- The runner serves limited (requester and viewer) clients even though its own session check
  found that its sshd lets a pty or an agent reach the forced command.
- If a downgrade already stood, the bridge's write raised its event epoch, and that raise is
  lost. The owner's attended lift then succeeds against recheck evidence that the lost event
  should have made stale: `lift_runner_downgrade` (`ext_runner.rs:374`) lifts while the row is
  still at the epoch the owner judged ("evidence taken at an earlier epoch never lifts a later
  one", `:127`).

Both are lasting effects on remote trust. The trigger is a remote party's session concurrent
with the owner's own first start, so §2.1 (a) and (b) both hold.

**Likelihood:** low.
- Adoption happens once per home, and only on homes a pre-release build created (ADR-0014
  §3.2 item 8).
- The window is roughly the fence transaction's duration plus the bridge's busy-handler sleep:
  milliseconds.

The lead may weigh that. The same hazard comes back in U2b-3 for released homes, though. A
restore or reset that reads the old generation (the carry-forward) and switches the pointer
while the bridge writes the old generation loses the write the same way. Fixing the bridge now
covers both.

**Evidence (SQLite semantics, not Heimdall code).** A model of steps 2 to 5, in WAL mode as
every store is, run with `python3 -I` in a scratch directory that has since been removed:

```python
bridge = sqlite3.connect(flat, isolation_level=None)   # bridge_record_with's connection
fence  = sqlite3.connect(flat, isolation_level=None)   # layout::fence
bridge.execute("PRAGMA user_version")                  # 2. check_version: 14
fence.execute("BEGIN IMMEDIATE"); fence.execute("INSERT INTO meta VALUES('adoption_fenced_from','14')")
fence.execute("PRAGMA user_version=2000000000"); fence.execute("COMMIT")      # 3. the fence
sqlite3.connect(flat).execute("VACUUM INTO ?", (copy,))                       # 4. the copy
bridge.execute("BEGIN IMMEDIATE"); bridge.execute("INSERT INTO meta VALUES('runner_owner_only','{...}')")
bridge.execute("COMMIT")                                                      # 5. succeeds
```

Output:

```
bridge check_version sees user_version = 14
bridge commit succeeded on a family whose user_version is now 2000000000
row in the fenced flat family (residue, never served): 1
row in the adopted copy (the generation that is served): 0
```

**Suggested fix (for the implementer).** Inside the bridge's `BEGIN IMMEDIATE` transaction,
read `user_version` again and refuse if it is the adoption fence. The refusal then queues the
marker (fail closed).
- Any bridge transaction that gets the write lock after the fence then sees the fence.
- Any that committed before the fence is in the copy.

For U2b-3 the bridge also needs to confirm, inside that transaction, that the pointer still
names the generation it opened. Alternatively, the restore holds a write transaction on the
old generation from its carry-forward read through the switch. A regression test fits the
store's adversarial set: a connection checked before the fence and committing after the copy.

## W3-R02: `run --parent-binding` reports its minted request ID without the epoch (not blocking)

**Where:**
- `crates/heimdall/src/delegate_cmd.rs:153-158`. It reports
  `output::diagnostic("heimdall: request ID {minted}")` before connecting, and never states
  the epoch.
- `crates/heimdall/src/cli.rs:1873-1874` routes `Command::Run` with `--parent-binding` here.
- Compare `crates/heimdall/src/run_cmd.rs:299-306`. Follow-up B made the `--profile` path say
  `retry with --request-id <id> --request-epoch <n>`.

**The contract:**
- ADR-0014 §3.6 step 3: "wherever they persist or pass on a request ID for retry, the epoch
  travels with it".
- The units doc §2b, follow-up B: "the epoch appears beside the request ID ... in `run`'s
  minted ID". The delegated form is the same `run` command (`RunArgs`, with `--request-epoch`).

**The scenario:**
1. `heimdall run --parent-binding <b> -- <cmd>` without `--request-id`.
2. The stderr hint tells a person or a script to retry with `--request-id <id>` alone.
3. That retry is bound to the epoch of the new session's hello. After a restore that lost both
   the old store and the ledger, the epoch check is then the whole fence (§3.6 step 5), and a
   re-stamped ID passes it.

Today no restore exists, so nothing can happen yet. After U2b-3 the restore ends the parent
binding, which bounds the effect. The JSON envelope carries both `request_id` and
`request_epoch`, so agents reading JSON are not affected.

**Tests:** `retry_args_are_taken_back_as_reported` (`cli.rs:3256`) and
`run_reports_its_minted_request_id_with_the_epoch` (`tests/e2e/request_epoch_cli.rs:250`) cover
only the `--profile` path.

**Fix:** report the minted ID after `connect_as`, through `retry_args(&request_id,
client.bound_epoch())`, as `run_cmd` does.

## W3-R03: the Windows switch fault set never exercises H15's write-through rename (not blocking)

**Where:**
- `tests/evidence/artifacts/m08/pc-job63-a9b038a7/README.md:9`. It says:
  "`adversarial_store_generations` | 6 passed ... This is the switch set with `MoveFileExW`
  write-through (H15)".
- `crates/runtime/src/state_store.rs:110-114`: `open_locked_with` is documented as "the fault
  tests' `FaultFs` around `PlatformFs`".

**What is wrong:**
- `adversarial_store_generations` is hosted by `heimdall-store` (`crates/store/Cargo.toml`),
  which cannot depend on `heimdall-runtime`, where `PlatformFs` lives.
- Every fault case runs `layout::open_locked` over `RealFs` or `FaultFs<RealFs>`
  (`tests/adversarial/store_generations.rs:74-80`, `:279-280`, the child at `:433-434`).
- `open_locked_with` has **no caller** in the tree (checked with grep).
- On Windows, `RealFs::rename_over` is `std::fs::rename` followed by a flush. Production's
  `PlatformFs::rename_over` is `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` with no flush
  after it.

So H15's rename has never run under an injected error or a kill. It does run on the ordinary
path on Windows: `e2e_store_generations`'s Windows test, the uninstall purge test that
publishes through `PlatformFs`, and every runtime start. The record overstates what job 63
proved. AGENTS.md's evidence discipline applies.

**Fix:** either correct the record and `open_locked_with`'s doc, or give the switch set a
`FaultFs<PlatformFs>` run. A small fault test in `heimdall-runtime` through `open_locked_with`
would do, run natively on Windows at the merge candidate.

## W3-R04: an interrupted layout removal in the purge cannot be finished by Heimdall (not blocking, low)

**Where:**
- `crates/heimdall/src/purge_sweep.rs:105-130` (`LAYOUT_ENTRIES` and its comment) and `:910`
  (`remove_layout`).
- `:597` (`family_dir`) and `:890` and `:2462`: `Anchors::open` refuses when the pointer names
  a generation that does not exist.
- `crates/heimdall/src/uninstall_cmd.rs:2551` and `:2621`: `--purge-state` refuses
  "the state store's pointer is damaged".

**The scenario:**
1. `uninstall --purge-state` deletes the family, then dies, or hits an I/O error, after
   removing `generations/` and before removing `CURRENT`.
2. The next runtime start is `state_corrupt` (`generation_missing`), as the comment says.
3. A re-run of `uninstall --purge-state` is also refused: `db_path` fails, and `Anchors::open`
   would refuse the missing generation too.
4. In this build the only way out is deleting `CURRENT`, and any other leftovers, by hand.
   The `state reset` and `state restore` skeletons answer "not available".
5. For an I/O error, the `stuck` list says what to remove. For a crash, the next run only says
   the pointer is damaged.

Nothing the owner did not confirm is lost, so this does not block.

**The record:** the residual `purge_layout_removal_interrupted_leaves_state_corrupt` is named
only in this comment. It is not in `docs/user/limitations.md`, the claims or the units doc's
§2b, and it understates the state: the purge itself cannot be re-run either.

**Fix:** record it. Or let the purge treat a pointer whose generation is gone, with no
`.hm-purge-*` unit present, as "layout removal unfinished" and finish the remaining
`LAYOUT_ENTRIES` under the lock.

## W3-R05: an interrupted first install plus a pre-release build leaves start-up refused (not blocking, low)

**Where:**
- `crates/store/src/layout.rs:253-268` (`first_publication`) and `:332` (`adopt`).
- `crates/stategen/src/generations.rs:426-430`: `StateDir::adopt` accepts only `Empty` or
  `FirstPublicationPending` with an **Adopt** intent.

**The scenario:**
1. This build's first start (an install) is killed, or hits an I/O error, before the pointer
   rename. That leaves a pending `Install` intent and no pointer.
2. A pre-release build is then run on the home. It knows no generations and creates a flat
   `<state>/state.db`.
3. This build starts again: `FirstPublicationPending{Install}`, then `probe_flat` finds the
   flat store, then `adopt`, then `StateDir::adopt` returns `Refused(WrongState)`.
4. Every start then fails with "state layout: refused: WrongState" until `STAGING-INTENT` is
   deleted by hand.

No data is lost. The limitations entry covers a pre-release build on a home this release
installed, as a second identity. It does not cover this stuck state.

**Fix:** an unfinished `Install` intent whose staged generation is already discarded can yield
to a flat store that appeared since (adopt it). Alternatively, extend the limitation's wording.

  carry-forward read and switch (see above).
- **Stale references "never as not found" (§3.6 step 2).** This wave records the epoch only as
  a column (`operations`, `decisions`, `remote_effect_outbox`). A reference presented after a

## Checked and found sound

**U3c:**
- `heimdall-testkit` is optional behind the default feature `test-config`.
- `build-release.sh`, `build-release.ps1` and `release-gate.sh` build with
  `--no-default-features`.
- `provenance.py` refuses `test-config` and `--all-features`, and refuses any test-only crate
  in the compiled set or the graph.
- A debug build without the feature is a `compile_error!`.
- The release gate's `cargo tree -i` probe fails closed on any output.

**U2b-1:**
- **Pointer-only start-up.** `open_locked` serves only the generation `CURRENT` names, after
  the record and file checks. A corrupt layout is `state_corrupt`, with no fallback to another
  generation or to the flat family.
- **Generation names** cannot leave `generations/`.
- **Adoption** follows the ADR's order:
  - intent, then the fence;
  - the fence is one IMMEDIATE transaction that keeps the old version in `meta`;
  - the copy is `VACUUM INTO` over a connection that opens the whole family, including its log;
  - the copy's version is restored, its fence key removed and its environment checked;
  - then the switch, then completion.
- **Adoption edge cases:**
  - the adoption resumes after the fence;
  - a fenced family with no intent is refused;
  - the flat family is probed before the intent, so a newer or damaged store is refused with
    nothing written;
  - an older build's step list reads the fence as `NewerSchema`.
- **Install** stages through `Store::open` and closes in DELETE mode, and stategen refuses any
  leftover `-wal`, `-shm` or `-journal`.
- **Migration** happens in place, with its backup in the generation, and the notes are rebuilt
  from the version found.
- **Every reader follows the pointer:**
  - `doctor`;
  - the CLI's read-only opens;
  - the M06 readers and direct writers, under the lock;
  - uninstall and its inventory;
  - the purge's anchors;
  - the bridge's path;
  - the issuer child's read-only open.
- **`quarantine_leftovers`** also checks the family of the generation the pointer names.
- **Windows:**
  - `MoveFileExW` with constant flags and NUL-checked wide strings;
  - files flushed before every rename;
  - generation directories judged by `judge_inside` before the open, and again after a first
    publication.
- **Unix:** directories are created `0700` and files `0600`.
- **The purge** anchors the current generation, deletes the family there, then the layout with
  the pointer last, all under the lock. A damaged pointer refuses. A fenced flat family reads
  as changed, which also refuses.

**U2b-2:**
- **The check order on every path** is: role and attendance checks, then the uninstall-fence
  admission (held across what follows), then the frame epoch, then the decision's minted epoch,
  then the fence lookup, then the ledger append and sync, then the request. The paths are:
  local requests, paired requests routed to the application, paired requests the runner
  answers itself, the runner's local `decide`, and the route/transport local `decide`. One
  exception: on the runner's local `decide` path, the attendance check sits inside
  `decide_local`, after the epoch check. `decide` carries no request ID, so nothing is appended
  to the ledger either way.
- **Stamps:** every answer the dispatcher gives a mutating request carries the request ID and
  the bound epoch. A refusal by the session before dispatch is not stamped.
- **A frame epoch** on a session that did not negotiate `request-epoch/1` is refused before
  dispatch.
- **The ledger digest** is the canonical JSON of the full idempotency key:
  - it equals the domain key's canonical form for every journaled kind;
  - `Request::kind()` equals the journaled kind, as the `m02` contract test checks;
  - principal, role, client and kind each separate the digest.
- **Fence verdicts** follow ADR-0006 §7.4:
  - an unresolved fence is never purged;
  - a partly settled row fails closed;
  - an undecodable stored answer still fences.
- **A damaged or unreadable ledger, or an I/O failure,** refuses every request that carries a
  request ID (`STATE_UNAVAILABLE` / `ledger_damaged` / `owner_decision`), and nothing runs.
- **Minted rows:** an epoch above 0 is recorded on operations, idempotency rows, decisions and
  outbox effects.
- **The hello** reports the epoch only where `request-epoch/1` was negotiated. The requester
  role holds the capability; the viewer does not. The bridge re-serializes `request_epoch`.
- **Clients:**
  - a kept epoch facing a runtime without the capability is refused `SCHEMA_UNSUPPORTED` with
    nothing sent; a fresh request goes without an epoch;
  - all 20 `--request-id` commands take `--request-epoch`, which requires `--request-id`;
  - `environment invite` keeps the runner's epoch and sends no local mutating request with it;
  - the TUI keeps the epoch of the first send;
  - the wrapper's `MUTATING` set is complete;
  - H2 has the `REQUEST_STALE` row (exit 6, `new_request_id`);
  - H1 reads the code table live.
- **Follow-ups A and B as ruled,** apart from W3-R02.

**U1b:**
- **M06-F3:** a debug build's `SshPaths::resolve` refuses a test configuration without
  `HEIMDALL_TEST_SSH_HOME`.
- **M06-F5:** an unusable `ProgramData` is refused, and the message never shows its value.
- **`alias_collision`:** a pure literal comparison over the include walk's user files only.
- **ISS-F1:** the orphan message carries no passphrase.

**Leak scan:** the diff, the evidence records and the probe facts hold no home path, canary or
