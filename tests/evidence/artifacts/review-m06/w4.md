# M06 wave 4 review (c4e9a5b5, diff dc69bbd4..c4e9a5b5) — independent reviewer

**Verdict: MERGE** (no blocking finding; R01 and R02 are moderate and should be fixed or recorded before M06 exits)

## Findings

### M06-W4-R01 — moderate (fail-closed; permanent issuance block with no way out)
`crates/app/src/remote_status_barrier.rs:61-94` (`lift_shown_among`), `:528-575`; `crates/app/src/remote_status_driver.rs:1281` (`delivered_holds`); `crates/app/src/remote_env.rs:289`.
`lift_shown` is false for a delivered pause/cutoff whose runner acknowledgement lists no applied policy (`!policies.is_empty()`), and for one naming a policy the runner no longer lists. A local `policy cutoff --all` fans out to every owned runner (`cutoff_all_on_runners`), including runners with no standing policy. That is the normal W4 case: a runner used only through forwarded `ensure`. Its acknowledgement then reads `policies: []` (`crates/remote/src/sync.rs:223`). `resume-issuance` can write the ack row and the runner can clear the cutoff locally, but the barrier still refuses `PolicyCutoff`, because the `fired` check and the "all" revision row both stay.
Recovery: none. `environment remove` does not clear the outbox or the ack rows (see R03), so a re-add keeps the block.
Probe (temporary, reverted): in `remote_status_driver::tests`, an `all` cutoff delivered with `policies: []`, runner report shows no cutoff, `resume_issuance_named` acknowledges 1, then `permit_answer` returns `Err(PolicyCutoff)`. The test failed as predicted (`exit 101`).
Suggested fix: for a scope-`all` effect with an empty or unlisted applied set, accept the owner ack plus a report with no remaining cutoff or pause on any listed policy and no `all` cutoff revision row. Or give the owner an explicit attended way to retire the effect.
Severity: owner's own action, fail closed, no trust or data effect, so not blocking under ADR-0009 §2.1.

### M06-W4-R02 — moderate/low (scope drift: record source (b) code is in W4)
`crates/app/src/remote_status_driver.rs:529-625` (`covering_policy`, `adopt_under_standing_policy`), called from `maintain` at `:1022` (result ignored). `tests/integration/controller_driver_m06.rs:~940`.
The commit message and the brief say source (b) is not in W4. The code is there and runs on every hosted pass, driven by the runner-supplied `AuthorityReport.pending_grants` (`runner_effects.rs:82`).
It is unreachable in production today. A policy can only name a managed-set environment (`admit_all`, `resolve_environment`, `managed_set`). Runner environments are not in `managed_environments`, so `p.environments.contains(runner_env)` is never true. Its test inserts the policy with `upsert_policy` directly.
It is one change (W5's `policy create --environment <runner-env>`) away from a runner-originated pending grant being auto-adopted. The code does bound it correctly: one policy, personal, active, same profile, all pairs inside the policy, PTY extension only, expiry no later than min(grant, policy window, cutoff). But W5's own review should be the first to see it live.
Suggested fix: remove the call (keep the function and test for W5), or state in the plan that the code is dormant.

### M06-W4-R03 — low
`crates/store/src/ext_effects.rs:630`, `crates/store/migrations/0012_remote_lift_acks.sql:9-12`.
The migration comment and module docs say ack rows "go with the environment's outbox rows when the controller forgets the environment". `forget_remote_effect_outbox` has no production caller. `ControllerRecordRequest::RemoveEnvironment` (`crates/app/src/remote_env.rs:289`) deletes only the pin. After `environment remove` and a re-add of the same runner (same environment ID), old outbox rows, old ack rows and delivered grants persist. An earlier ack can reopen after a re-add. A stale unacknowledged hold keeps blocking (see R01).
The ack keys name specific delivered effects, so a later cutoff is never pre-acknowledged. Same-user and owner-only; low.

### M06-W4-R04 — low
`crates/app/src/remote_status_driver.rs:308-314` (`deliver_runner_grant`).
A second forwarded `ensure` that attaches to the same grant (subset of pairs, earlier deadline) intersects the controller's one delivered record. Pairs and expiry for the whole grant narrow, so after a later `resume-issuance` the first binding's other pairs are no longer re-issued. It only narrows, so it fails closed, but it is surprising. A per-binding record would fix it. Record it.
