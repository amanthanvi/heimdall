### W6-R01 — Windows lock preparation/cleanup can leave the real account projection behind and delete its recovery state

**Severity: blocking by ADR-0009 §2.1.** Primary locations: [tests/e2e/exit_m03/lock.rs:1409](tests/e2e/exit_m03/lock.rs:1409); also [tests/e2e/exit_m03/lock.rs:1543](tests/e2e/exit_m03/lock.rs:1543), [tests/e2e/exit_m03/lock.rs:354](tests/e2e/exit_m03/lock.rs:354), [tests/e2e/exit_m03/world.rs:566](tests/e2e/exit_m03/world.rs:566), [tests/e2e/exit_m03/world.rs:1049](tests/e2e/exit_m03/world.rs:1049).

`owner_ssh_guard` treats an absent or empty account `.ssh` as proof that the account is disposable. It does not establish that identity or authorization. The documented Windows invocation runs in the owner's interactive session. An owner with no existing SSH configuration therefore passes the guard. `WorldOptions::product` then uses the account database's real home: `setup apply` writes that account's `.ssh/config`; setting the process's `HOME` to scratch does not isolate this operation.

An ordinary error after successful `setup apply` (for example the subsequent `time confirm` failing or timing out) unwinds `World::start` before `slot = Some(run)`. The world destructor stops its runtime but never rolls back the account projection. The outer preparation-error path reports cleanup as successful. Its scratch home, including the projection's state/backups, is removed. Even after preparation succeeds, `Run::cleanup` accepts any rollback exit code and catches rollback panic/timeout as text, then drops the world and deletes the recovery directory anyway. An after-the-fact owner digest can fail the harness; it cannot restore the lost recovery state.

**Concrete effect/trigger:** run the Windows lock procedure in an ordinary owner's account whose `.ssh` is empty; an I/O error or failed/time-limited attended command after projection apply leaves the real SSH configuration referencing removed scratch material, while the state needed to undo that apply is discarded. No hostile same-user program is needed. This also affects a deliberately disposable account's recovery record on the same error path.

**Probe:** compiled the unchanged `owner_ssh_guard` function extracted from the reviewed source with only `account_home()` replaced by a fixture-home provider. Compilation exit **0**, execution exit **0**: absent `.ssh` accepted, empty `.ssh` accepted, populated `.ssh` refused. No owner's home was read. The interrupted Windows preparation was **not** run; the unwinding/deletion result is source evidence, not a native observation.

**Required correction:** establish a disposable account independently of directory emptiness; keep rollback/recovery ownership from the moment projection apply can happen, including preparation failures; verify restoration and retain recovery state if it cannot complete. Refusing the owner account is appropriate; a stub's `owner_ssh_in_scope` message does not prove the real guard does that in every permitted case.

### W6-R03 — Custody validation checks the claim's labels, not the evidence row's profile/store provenance

**Severity: non-blocking at this commit; must be resolved or explicitly checked during the future claims update.** Locations: [tests/native/m03/m03-evidence.py:44](tests/native/m03/m03-evidence.py:44), [tests/native/m02/m02-evidence.py:797](tests/native/m02/m02-evidence.py:797), [tools/validation/claims_table.py:561](tools/validation/claims_table.py:561).

**Probe:** used the validator's own `_entry_source`, `_record` and `_run_fixture` helpers with a verified `macos-arm64 (debug build, scratch test store)` row, host facts `build-profile=debug` and `store-kind=scratch_test`, and a claim declaring `Release`/`macos_login_keychain`. The actual validator returned **no errors**; probe exit **0**. Its ordinary self-tests also pass (exit **0**), because they vary the entry declarations rather than contradicting the evidence provenance. The source rule “only release/product rows qualify” is not fully enforced by this check.

### W6-R04 — A33 silently skips unreadable files while counting them as scanned

**Severity: non-blocking.** Locations: [tests/e2e/exit_m03/scan.rs:149](tests/e2e/exit_m03/scan.rs:149), [tests/e2e/exit_m03/scan.rs:194](tests/e2e/exit_m03/scan.rs:194), [tests/e2e/exit_m03/scan.rs:315](tests/e2e/exit_m03/scan.rs:315).

`scan_tree` ignores every failed file read and returns the number of discovered files, including the unread files. Directory iteration/metadata failures are also silently omitted. Crash-file reads have the same pattern. One readable CA-public positive control elsewhere does not establish that every required artifact was read. An artifact created with restrictive permissions, removed during scanning, or affected by an I/O error can contain a needle while the test reports zero hits and passes. These filesystem omissions are not added to `unobservable`, unlike explicit process-environment limitations.

**Probe:** compiled the actual scanner functions extracted from the source, created a disposable regular file containing a synthetic needle, changed its permissions to `000`, and confirmed that a direct read failed. Actual `scan_tree` returned **files_reported=1, hits=0**. Compilation exit **0**, execution exit **0**. The file permissions were restored and the fixture removed. Propagate read failures or explicitly record incomplete coverage; count successful reads separately.

### W6-R05 — The managed-certificate builder still uses a pair ordinal in the serial field

**Severity: non-blocking; pre-existing product inconsistency, expressly checked because the task asks about other key-ID builders.** Locations: [crates/app/src/managed/driver.rs:303](crates/app/src/managed/driver.rs:303), [crates/app/src/operations.rs:11752](crates/app/src/operations.rs:11752), [tests/e2e/exit_m03.rs:228](tests/e2e/exit_m03.rs:228).

The verification fix correctly generates the key ID after allocating its random serial. The managed-activation path still constructs the suffix from `n + 1`, before `reserve_issuance` allocates a separate random serial. Re-issues of a grant/pair can thus reuse a key ID despite having new certificate serials. This satisfies the current issuer's numeric-suffix ceiling, so it does not reproduce the old verification `positive`/`negative` rejection, and the lifecycle tests still attribute by grant plus the separately decoded certificate serial. It disagrees with the documented `...:<serial>` format and makes a key-ID-only audit ambiguous.

**Probe:** the real activation/re-issue/revocation run passed, exit **0**, and printed `key_id_last_field=not_serial`. The new test deliberately records this mismatch instead of asserting it. No broader certificate authority or grant extension was demonstrated. This does not invalidate the verification fix, but the same family of formatting assumption remains elsewhere.

### W6-R06 — macOS artifact scanning detects a canary after saving it, then retains it

**Severity: non-blocking under ADR-0009 §2.1 because the material in scope is disposable fixture output.** Locations: [tests/native/m03/lock-lib.sh:269](tests/native/m03/lock-lib.sh:269), [tests/native/m03/run-macos.sh:72](tests/native/m03/run-macos.sh:72), [tests/native/m02/lib.sh:207](tests/native/m02/lib.sh:207).

The new macOS lock/Docker finish paths run the general redactor into the final evidence files and then count canary prefixes. That redactor removes paths/names/addresses, not canary values or arbitrary secret bytes. A nonzero count fails the run but leaves the original sensitive text in the saved artifact. A failed run must not become a public evidence attachment containing its fixture secret. The Windows lock path at least counts and masks canaries before writing its bundle; it does not supply an equivalent arbitrary-secret-byte filter.

**Probe:** passed one synthetic canary value through the actual `m02_redact` and `m02_canary_scan` helpers in an owned temporary directory. Detection count **1**; `cmp -s` confirmed the final saved file was byte-identical to the input and still contained it. Probe exit **0**; no canary value was printed, and the fixture was removed. Quarantine, suppress, or sanitize contaminated output before retaining/publishing it; preserve a nonsecret failure record.

**Harness safety.** Apart from R01, the reviewed default paths use scratch homes, explicit test configuration, fixture CA/agent material, and loopback SSH servers. The external sshd adoption checks loopback addresses and receives files created by its harness; it does not stop the external server itself. No blanket `wsl --shutdown` or other-distribution unregister was found. Owner digests and keychain search-list inspection are observational. The macOS keychain test path uses disposable file keychains, not login-keychain custody. R06 qualifies the saved-artifact safety claim. None of these native guarantees was closed by emulation or by this local stub test.

**Meaning of A10.** The local test demonstrated real binding login, endpoint identity listing with certificate/serial controls, no advertised issuer path, no issuer sockets, and no issuer-pipe descriptors in the bound worker on the observed macOS run. It explicitly reported that macOS keychain reachability and other processes' environments were unobservable, and kept `issuer_isolation=same_user_process`. It is an observation of these surfaces, not an isolation proof against the same OS user. On Windows it compares a worker's DPAPI read against a scratch-item control; the native Windows result remains unrun here. Failed descriptor reads in “other runtime children” are skipped at [tests/e2e/exit_m03.rs:536](tests/e2e/exit_m03.rs:536); the zero statement there should not be read as proof for unreadable children. R02 currently removes the recorded qualifications from generated row observations.

**Meaning of A33 and the real issuer lifecycle.** A33 exercises output/state/projection/worker artifacts across activation, runtime restart, reports, events and revocation, with known CA bytes and 16 possible seeded environment-key indices. It checks that all four actual activation/re-issue public keys match scanned private-key seeds. It explicitly exempts the placed environment entry and test adapter receipt references; it runs no passphrase ceremony and therefore does not by itself prove D5 passphrase handling. It reports inaccessible process environments rather than observing them. R04 prevents claiming exhaustive file coverage, and server logs outside those selected trees are not scanned by this function.

The lifecycle test is substantive: it checks one published activation per grant, authenticates via the binding with server-log attribution to the grant/CA/serial, restarts the runtime in the same boot, observes new published serials and a changed subject-key fingerprint, and then requires binding/projection login refusal and no accepted server-log entries after revocation. It proves fresh local authentication stops, not termination of an already-running remote command. The verification test adds the distinct positive/negative enrollment boundary. A33 repeats lifecycle operations to produce artifacts for its scan; that serves a separate observable property, so it is not a separate blocker or a proposal for more duplicate tests under ADR-0009 §2.3. Child entry tests are harness infrastructure, not independent product-behavior evidence.
