## Changes
- Item 1 (`recover_unit`'s marker branch, Unix + Windows, purge_sweep.rs): the existing pre-checks stay (binding, `ops.check`, binding again; each original's recorded identity). A new test hook `recover-checked` follows them. Then the copy is restored as state.db by one no-replace rename, and the file at the live name is verified from a fresh read (binding, `ops.check`, binding again). Only after that are the originals, the marker, the record and the directory removed. If verification fails, nothing is unlinked, the unit is kept, and the file at state.db is reported. That uses a new `Recovered::unverified` field and an extra clause in uninstall_cmd's refusal ("does not match the recovery copy the deletion mark binds (not verified ...)"). The same report covers a copy that was already restored but does not match. Start-up keeps refusing (tested).
- Item 2 (`Unit::delete`, both platforms): after the unlink hook and before the first original is unlinked, the copy's binding is read again by name through a fresh descriptor. On a mismatch it uses `keep`: nothing is unlinked or restored, and the unit and its marker stay, so a later recovery also refuses.
- Item 3 (Windows): `hold_copy` opens the copy with GENERIC_READ and share READ|DELETE (no FILE_SHARE_WRITE), never following a reparse point, and checks the file ID. On the normal path the hold lasts from the copy check through the last original unlink. In recovery it lasts through the restore and its verification. The restore renames through the held handle via a new safe wrapper, `heimdall_ipc::windows::rename_held_no_replace` in crates/ipc/src/windows.rs (an overview §9 module): ReOpenFile(DELETE, share READ|DELETE), then SetFileInformationByHandle(FileRenameInfo, ReplaceIfExists=false), with a `\\?\` full path.
  - It prevents: any other open for writing or truncating (sharing violation, same user included); and an already-open writer makes the hold fail, so the purge refuses. Reads still work (std read, `pin`, SQLite's read-only open with share READ|WRITE). A file put at the copy's name is never the one restored.
  - It does not prevent: a rename or deletion of the copy (the hold has to share delete for its own rename), attribute/ACL/timestamp changes, writes after the hold is released (the live state.db is P03), any Unix window, or another handle without share-delete making the restore fail (fail-closed).
- Item 4: added RESIDUALS `purge_recovery_copy_overwritten_between_check_and_unlink` (NeedsHostileSameUserProgram, platform `any`, adr "ADR-0008 §17.39"). Its probe is `uninstall_cmd::tests::w5_j01_copy_overwritten_after_check_keeps_originals`. I followed round 15, whose "§17.38" was written before the ADR had it; the tests only need a non-empty adr string.
