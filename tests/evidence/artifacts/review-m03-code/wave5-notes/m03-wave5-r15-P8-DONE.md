## Changes
- W5-I01 (purge_sweep.rs, both platforms). The deletion marker binds the copy: `copy\t<dev>\t<ino>\t<size>\t<sha256>`. `Unit::delete` first checks that the copy at its name has the identity it was written with, then `verify` (`uninstall_cmd::copy_reads`: opens read-only and no-write on its own, integrity, schema, `Inventory::read_store`), then re-checks the binding, and only then creates the marker (O_EXCL, synced; dir fsync on Unix). The marker is now removed after the originals and before the copy, so a marker never outlives its copy. On the marker branch of `recover_unit` (Unix and Windows), before any unlink: the marker parses; the copy (in the unit, or already restored as state.db) matches the binding before and after `RecoverOps::check`; every original present has the recorded dev/ino or file ID. The one exception is an unrecorded, empty, purge-created companion (not the db). Any failure keeps the whole unit (`all_left`). Start-up keeps refusing.
- RESIDUALS: added `purge_recovery_copy_and_marker_forged_together` (NeedsHostileSameUserProgram, probe w5_i01_planted_marker_with_garbage_copy_keeps_database, the other W5-I01 tests named in its text, adr "ADR-0008 §17.38"). `purge_entry_placed_in_quarantine_is_deleted` no longer says owner data is never deleted; it describes the mark/binding checks and points to the new residual.
- F2: `read_family_no_write` reads in place only when both -wal and -shm exist. Observed with the fix reverted: the in-place open did not fail; it created an empty `state.db-wal` (an actual write).
- Windows: `read_with_wal` is #[cfg(unix)] (its only users are the Unix census probes). Every round-13/14/15 database-family test is ungated. Two tests use FAIL_UNLINK on Windows instead of chmod 0500 (Windows has no directory write bit): final_review_companion_failure_preserves_database, final_review_recovery_copy_holds_every_record_by_itself. Windows test hooks were added (step restore/copy-written/delete-copy, move, unlink).
