## Findings

### M07-W5-R01 — moderate, nonblocking — a timed-out release is forgotten and can be resent; cleanup can also skip every other binding

**Locations:** `examples/harnesses/goal-loop/harness.py:815`–819, `:1034`, `:1125`–1129. The uncertainty/history update is later, in `settle` at `:886`–909.

**Failure:** `subprocess.run` can time out after dispatch, including after receiving a complete `OUTCOME_UNKNOWN` JSON line. `invoke` discards `TimeoutExpired.stdout` and raises before `settle` records anything. The planner leaves both `attempts` and `uncertain` empty. `close()` treats that binding as an ordinary releasable binding and sends the release again without observing it. If it times out again, `close()` sees that the round made no recorded attempt, breaks, and never tries the other held bindings.

**Reproduction run:** an independent scratch Python subprocess stub printed a complete schema-1 `OUTCOME_UNKNOWN` answer, `effect_status: unknown`, with `next: {action: reconcile, operation_id: op_fixture}`, flushed stdout, then slept for five seconds. Only the review invocation patched `CALL_SECONDS` to 0.25 seconds. A second release answered ordinary `OK`. The observed calls were:

```text
access ensure
access release binding_fixture
access release binding_fixture       # close, with no operation wait or inspect between
```

The failed stop had no release attempt and no remembered uncertainty. Close reported `released: [binding_fixture], held: []`, and history contained only the close's successful release. An always-timeout variant, seeded with three synthetic held bindings, sent `release binding_newer` in the stop and again in the close, recorded zero attempts, and left all three held; neither older binding was asked about. Both subprocess probes exited 0 because they asserted these observed failures.

**Required behavior:** preserve an uncertain attempt once a release may have been dispatched, including timeout/unreadable-response paths; observe it before another release. Keep failed per-binding cleanup from preventing bounded attempts on other bindings. A known pre-dispatch launch failure can be treated separately.

**Limits:** no real Heimdall was used in this reproduction. The run still fails because the stop failed; this is a replay/audit/cleanup defect, not a reproduced exit-0 result. Current release is idempotent in the store (`crates/domain/src/binding.rs:6`, `crates/store/src/ext.rs:674`), and no lasting owner-data or remote-trust effect was demonstrated. The unresolved public semantics remain U0-Q7's decision.

### M07-W5-R02 — moderate, nonblocking — a nonterminal operation can be called a completed release

**Locations:** `examples/harnesses/goal-loop/harness.py:534`–546 and `:237` (`RELEASE_SAYS`'s successful observation row).

**Failure:** `read_operation` checks the operation ID and code, but does not validate its typed `state`. When `data.code` is null, it returns the lookup envelope's `OK`. `RELEASE_SAYS` reads `OK` / `none` / exit 0 as positive release evidence even when the view explicitly says `state: running`, `effect_status: unknown`, and `result: null`. The binding is then removed from both `held` and `uncertain` and recorded as `released`.

**Reproduction run:** a scratch subprocess stub first answered release with `OUTCOME_UNKNOWN` naming `op_fixture`. On close's `operation wait`, it answered schema-1 `OK`, next null, exit 0, with this data:

```json
{"operation_id":"op_fixture","state":"running","code":null,"effect_status":"unknown","result":null}
```

Observed sequence: `ensure`, `release`, `operation wait`; no second release. Nevertheless, close reported `released: [binding_fixture], held: []`, and its attempt was `{by: close, outcome: released, code: OK, exit_code: 0, observed: operation}`. The reproducer exited 0 after asserting that result.

**Required behavior:** require a terminal, successful operation view before recording an observed release. An active operation must stay unknown; a contradictory exit/action should be recorded as inconsistent. Likewise, require a terminal view before interpreting a non-OK recorded outcome with effect `none` as `not_run`.

**Limits:** this is a contradictory stub answer, not an observed real-binary response. The product currently sets `next: observe` for nonquiescent observations (`crates/app/src/operations.rs:10886`) and exits 5 for active waits (`crates/heimdall/src/output.rs:43`), so the nominal product path is protected by its own emitters. The example's claimed defensive handling is incomplete; no lasting effect or exit-0 overall run was reproduced.

### M07-W5-R03 — low, nonblocking — known release codes outside the reduced table never get an inconsistency marker

**Locations:** `examples/harnesses/goal-loop/harness.py:368`–386 and `:486`–488.

**Failure:** `EXIT_CLASSES` contains only the transition codes plus `NOT_FOUND`. Other published codes, such as `SERVICE_UNAVAILABLE` (documented class 5), are treated as having no known class. A release answered `SERVICE_UNAVAILABLE` with exit 0 is correctly refused, but its record omits `inconsistent: true` and the probable-product-defect detail. This falls short of rule 5's general wording and README's every-answer claim.

**Reproduction run:** a scratch subprocess stub emitted schema-1 `SERVICE_UNAVAILABLE`, next `retry_after`, nested error effect `none`, and exited 0 for each release. Both stop and close recorded `refused`, `code: SERVICE_UNAVAILABLE`, `exit_code: 0`, without `inconsistent` or `detail`. The reproducer exited 0 after asserting the omission. ADR-0013 §4 and the current public code table document class 5.

**Suggested correction:** check all published codes, using the installed table already read by discovery or the full frozen code table, while preserving the command-specific accepted/wait exceptions. The binding remained held and the run remains failed, so the demonstrated impact is missing diagnostic metadata.

### M07-W5-R04 — low, nonblocking — the handoff overstates two current consumer behaviors

**Locations:** `docs/architecture/m07-u0-handoff.md:40` and `:120`–122.

**Reproduction/evidence:** source inspection and executed stub cases; no additional product run needed.

- The H7 row says the wrapper and both harnesses read `inspect capabilities`. H2's complete call set at `examples/harnesses/goal-loop/harness.py:44`–64 has no such call; its discovery reads only `schema show codes`. H1 does read capabilities (`examples/harnesses/cli/harness.py:160`). Describe H2 as a prospective consumer or qualify the statement.
- U0-Q7 says an uncertain release with no named operation reports `still_unknown`, stays held and exits 1. That is the `active`/unreadable case only. H2 also accepts a listed `released` state, and removes an absent binding as `not_listed`; the shipped suite exercised both outcomes successfully. §5a and the README already describe the distinction correctly, so align Q7's consequence with them.

No implementation, consent or compatibility behavior changes because of these sentences.

## What I checked and found clean

- **Nominal release rules:** non-OK refusals are recorded and skipped while other bindings are released; refused stops fail even after subsequent successes. Recognized code/exit mismatches stay held and get the diagnostic marker. `OUTCOME_UNKNOWN`, including wrong-exit uncertainty, is separate from refusal. A later stop or close waits on its named operation or reads the binding list. `active` remains `still_unknown`; absent becomes `not_listed`, never `released`. A failed/cancelled operation with terminal no-effect evidence is the sole nominal resend route. An observation refusal's nested `data.error.effect_status` is not mistaken for the operation's own `data.effect_status`.
- **Stop boundaries:** the existing tests cover cut-short stops, continuation without reasking set-aside bindings, large binding sets, close as its own stop, uncertainty newly received by close remaining held, and ordered per-binding attempt summaries.
