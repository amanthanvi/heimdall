## Findings

**M07-W0-R01 — Blocking, a persistent Settings change can bypass informed confirmation.** `crates/heimdall/src/tui/m07.rs:1140`, `tui/view.rs:1219`, `tui/mod.rs:353`.
The Settings prompt accepts `yes` independently of what was drawn. At 40×5 the Pause confirmation showed neither the policy nor the command, yet Enter sent `Command::Setting(Pause)`. The same sequence sent it without any intervening frame. The input loop can process a whole batch before drawing, and the runtime applies narrowing and default-profile changes without a second modal.
Use the existing confirmation reading guard for Settings, with the action and its target visible before accepting input. An undersized screen must refuse submission until it can display the confirmation. Test both a batched input sequence and a short terminal. The current Settings test explicitly sends keys without drawing.

**M07-W0-R02 — Blocking, a refused projection can leave a durable catalog change.** `crates/heimdall/src/enroll_cmd.rs:483`, `:518`, `:529`, `setup_cmd.rs:917`, `crates/app/src/catalog.rs:1133`.
Verification already sets the managed preference before returning `SetupApply` (`crates/app/src/operations/enrollment_m03/verify.rs:610`). The guided flow shows the plan, asks whether to apply it, then separately writes the preference and submits the plan. If the owner changes the preference to Existing while that prompt is open, this extra write can undo their choice even if the digest is stale or they decline the subsequent recorded projection decision. A scripted runtime requiring projection approval produced three prompts and received `SetPreference` before the third answer was No. The plan itself remains digest-bound.
Remove the redundant preference write. Use the recorded decision as the projection confirmation when required, and a single digest-bound local prompt for a plan that can apply under saved consent. The committed test scripts immediate setup success. Add the approval-required branch and a changed-preference case.

**M07-W0-R03 — Moderate, a failed read can still look current or healthy.** `crates/heimdall/src/tui/worker.rs:585`, `:663`, `tui/model.rs:727`, `tui/view.rs:545`.
The scrollable list header is the only stale marker. Paging a 40×12 destination list after a failed read hid both that marker and the error, leaving ordinary rows. A transport failure can drop the session and prevent publication of the recorded error. Policy/workspace reads bypass the failure cache entirely, so Settings can show “none set” for a failed default-profile read. The overview treats even never-read failures as warnings and can still say “Ready” or “no work running.”
Keep a compact stale/error indicator outside the scrollable list, publish failed or disconnected state, and withhold reassuring claims when their source is absent or stale. Cover transport, first-read and scrolled failure cases. The existing listing test checks the first viewport and asserts Ready for a failure.

**M07-W0-R04 — Moderate, the TUI promises lock outcomes the runtime does not attest.** `crates/heimdall/src/tui/m07.rs:559`, `:831`, `tui/m03.rs:360`, `crates/app/src/lock.rs:295`, `:406`.
“Work continues” and “locking ends access” are rendered from the aggregate personal-policy setting. That setting omits workspace policy, says nothing conclusive about a particular running grant, and can be backed by an unverified signal or continuity claim. The runtime already supplies qualified disclosure text. Settings repeats the categorical claim in its confirmation.
Separate saved policy from observed continuity and carry the verification qualifier. Test mixed personal/workspace policies and unverified continuity. Existing A30 surface checks match wording without establishing the outcome.

**M07-W0-R05 — Moderate, the PowerShell prompt has no outer time or output limit and dirties `$Error`.** `crates/heimdall/src/activate_cmd.rs:737`, `:755`.
PowerShell 7.7 retained the original prompt text, its view of the preceding failure, and `$LASTEXITCODE`. The missing executable still added one `$Error` entry. A child that slept two seconds held the prompt for about 2.05 seconds. A hung startup or retained stdout handle can hold `ReadToEnd()` indefinitely. The Rust hook's internal timer cannot bound that wait.
Use a quiet missing-command lookup and a deadline covering child exit and bounded stdout. Test both missing and non-returning executables. The existing e2e tests bound the harness externally and check `$LASTEXITCODE`. The 7.x argument list and 5.1 quoted path are static, and no runtime-supplied string is evaluated. The 5.1 path was source-reviewed.

**M07-W0-R06 — Moderate, part of the TUI still rebuilds catalog-sized lists on keys.** `crates/heimdall/src/tui/model.rs:1265`, `:1308`, `tui/view.rs:788`, `:970`, `:1152`, `tui/m07.rs:1259`, `tui/data.rs:515`.

The product latency test's large catalog is observed destinations, which do not create Settings connection rows.

**M07-W0-R07 — Moderate, the TUI does not retry stale decisions for its own submissions.** `crates/heimdall/src/tui/model.rs:1487`, `tui/worker.rs:725`.
The stale handler is safe about discarding confirmation. It assumes every originating request came from elsewhere, including Settings changes that the TUI sent itself. It also clears any open decision modal regardless of which request failed. U2a calls for retry of the original attended request and a fresh confirmation.
Retain the originating request only for TUI-owned decisions and correlate the stale reply with that modal. Preserve the refresh-only behavior for externally originated decisions. Test both cases and an interleaved unrelated modal. The current test asserts the refresh-only path.

**M07-W0-R08 — Moderate, human status overcounts actionable decisions and only points at access details.** `crates/heimdall/src/output.rs:280`, `cli.rs:1805`, `crates/store/src/ext.rs:512`.

Count only live decisions in the new human summary and test a mixed live/expired listing. Cover the three answers with fixtures for active, paused and unavailable state. The existing unit test does not exercise expiry or a participant workflow.

**M07-W0-R09 — Moderate, protocol classification leaves two documented cases uncovered.** `examples/reference-wrapper/reference_wrapper.py:126`, `:133`, `docs/api/local-protocol.md:126`, `:149`, `crates/contract/src/code.rs:259`.
