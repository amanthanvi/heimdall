# Heimdall M07 W7: independent review

**Verdict: MERGE.** Under ADR-0009 §2.1 a finding blocks only when it has a lasting effect on remote trust, recovery records or owner data, or bypasses consent, *and* its trigger is an ordinary crash, an I/O error, the user's own action, a remote party or another account. None of the six findings below meets both conditions. All six are nonblocking: one moderate, four low, one nit.

- **Scope:** `git diff dd0c58fa e3f6858b`, the commits W7a `6a799570`, W7b `ff6745a1`, W7.1 `b2b3960a` and W7.2 `e3f6858b`. That is 23 files, +3774/−293.

## Findings

### M07-W7-R01: moderate, nonblocking. The identity guard checks only the destination. A ProxyJump or ProxyCommand hop starts a second, unguarded client.

**Where.** `crates/testkit/src/pinned_ssh.rs:450-463` (`check_effective` reads only `identitiesonly`, `identityagent`, `identityfile` and `userknownhostsfile`; every other key falls into `_ => {}`). The claims this contradicts are at `pinned_ssh.rs:28-34` ("never to the system pipe") and ADR-0007 §12.52 item 2, at `docs/decisions/0007-existing-access-integration.md:4941` ("so the in-box client can never fall back to the system agent pipe … or the account's default identities").

**What happens.** The guard accepts an effective configuration that routes the destination through a jump. OpenSSH builds the jump's client from ProxyJump with only `-F <config>` (plus `-l`, `-p`, `-J`, `-v` and the host). None of the wrapper's `-o` options reach it: not the pinned `IdentityAgent`, not the sidecar's `UserKnownHostsFile` or `GlobalKnownHostsFile`, not `ControlMaster=no`.

Win32-OpenSSH also sets `SSH_AUTH_SOCK=\\.\pipe\openssh-ssh-agent` in `wmain` whenever the variable is unset. The client applies its own `IdentityAgent` (setenv or unsetenv) only after `ssh_connect`. So a ProxyCommand, ProxyJump or LocalCommand child inherits the system pipe.

For a jump host whose scratch section sets nothing, the hop uses:
- the agent named by `SSH_AUTH_SOCK`;
- the default `~/.ssh/id_*` keys of the token's real profile;
- the real `known_hosts`, which is read, and written after a typed yes or under `accept-new`.

Heimdall's own projection renders `ProxyJump <jump alias>` for a routed destination, and `ProxyCommand "<heimdall>" route connect …` for an Iroh route (`crates/sshconf/src/render.rs:567`, `:735`). A future routed Windows row would therefore hit this gap without any unusual configuration.

**Reproduced on macOS** (`probe-pj/`, the built `hm-pinned-ssh`):
- **Setup.** The client was a script: it runs the real `/usr/bin/ssh -G` for the check and only records its argv otherwise, so nothing connected. The scratch config was `Host alpha` (ProxyJump bastion, `IdentityAgent none`, a scratch IdentityFile, `IdentitiesOnly yes`) plus a bare `Host bastion`.
- **Guard.** The wrapper printed `hm-pinned-ssh: checked: identity agent none`, exited 0 and started the client.
- **What the guard saw.** The guard's own `-G` output contained `proxyjump bastion`.
- **What the hop gets.** `ssh -G -F <config> bastion` is what the hop evaluates. It printed no `identityagent` line, `identitiesonly no`, `identityfile ~/.ssh/id_rsa` (and the other defaults), and `userknownhostsfile <real home>/.ssh/known_hosts …`.

**Source-derived for Windows:** from PowerShell/openssh-portable `latestw_all`:
- `contrib/win32/win32compat/wmain_common.c` sets the default `SSH_AUTH_SOCK` when it is unset;
- `ssh.c` builds the ProxyJump command with only `-F`, and places the `identity_agent` setenv/unsetenv after `load_public_identity_files`;
- `authfd.c` has no fallback pipe once the variable is unset, so `IdentityAgent none` itself does hold.

**Why it does not trigger today.** No current row uses a route: `jump: None` at `tests/e2e/cli_m02.rs:527` and `run_m02.rs:3145`/`:4485`. Also, A01 and A11 set `SSH_AUTH_SOCK` to the decoy, and both assert zero decoy contact, which would catch agent use by a hop. The default identities and the real `known_hosts` would not be caught.

**Why nonblocking.** The trigger is a future test's routed configuration, which is none of §2.1's triggers. The wrapper is test-only. A hop would be offered to a loopback fixture sshd.

**Smallest fix.** In `check_effective`, refuse unless `proxycommand` and `proxyjump` are absent or `none`, and unless `localcommand` is absent or `permitlocalcommand` is `no`. Alternatively, narrow the ADR and module claim to "the client the wrapper starts" and have a routed row check each hop with its own `-G`.

### M07-W7-R02: low, nonblocking. H1 and H2 accept the in-box `ssh.exe` as the `run` child without checking its isolation arguments.

**Where.**
- `examples/harnesses/goal-loop/harness.py:1701-1712`: `inside or bool(client) and PureWindowsPath(argv[0]) == client and program.is_file()`.
- `examples/harnesses/cli/harness.py:75-83` and `:259-264`.
- `goal-loop/README.md:88-90` says "the driver then gives it its scratch config and the isolated options".

**What happens.** Before W7, any child outside the scratch root was refused. Now a Windows goal like `{"goal":"run",…,"argv":["C:\\Windows\\System32\\OpenSSH\\ssh.exe","<host>"]}` is launched as given. That client reads the token profile's real `%USERPROFILE%\.ssh\config`. H2's launch environment never passes `SSH_AUTH_SOCK` (the stub asserts it is absent), so `wmain` points the client at `\\.\pipe\openssh-ssh-agent` unless the argv says `IdentityAgent=none`.

`tests/e2e/harness_m07.rs:45-55` describes this very hazard and avoids it by construction: `task5_child` passes `-F`, `IdentitiesOnly=yes`, `IdentityAgent=none`, `-i` and scratch known-hosts files. The harnesses themselves no longer enforce it.

**Status.** Source-derived; Windows only.

**Why nonblocking.** Goals come from the test driver, the harnesses are fixture-only examples, and no lasting effect was shown.

**Smallest fix.** For the in-box client, require `argv[1:]` to carry:
- `-F` naming a file inside the root;
- `IdentityAgent=none`, or a scratch or fixture value;
- `IdentitiesOnly=yes`;
- `UserKnownHostsFile` and `GlobalKnownHostsFile` inside the root.

Refuse otherwise. Alternatively, have the driver start a scratch copy of `hm-pinned-ssh`. It lies inside the root, so the old rule holds, and its guard checks the effective configuration.

### M07-W7-R03: low, nonblocking. On Windows, H2 "ends the child" by ending `heimdall.exe`, and the real child keeps running.

**Where.**
- `examples/harnesses/goal-loop/harness.py:1152-1170`: `Child.end` closes stdin, then calls `terminate()` and `kill()` on `self.process`.
- On Windows `self.process` is Heimdall: `LAUNCHED["nt"]`, and `launching.pid` is Heimdall's own PID (`:670-675`).
- `README.md:218` says "Any other sequence is no launch, and the child is ended". The `Child.end` docstring says "a child that stays is stopped by this handle".

**What happens.** The product's own Windows test records that a forced launcher kill leaves the child running: `tests/e2e/run_m02.rs:1660-1705`, and PC job 49's log line `limitation recorded: a forced launcher kill releases the binding while the child runs`. So on Windows a child that ignores end-of-input survives H2's stop, close or failed launch. So does a child that is up when H2 ends the launch through `end(1)`, for example after a record sequence that is not a launch. The PID in the `spawned` record is never used.

The stub cannot show this, because on Windows it writes `spawned` with its own PID: the stub is both Heimdall and the child. The real A32 task 6 passes only because the in-box client exits at end-of-input.

**Status.** Source-derived, plus the product test's recorded limitation.

**Smallest fix.** On Windows, after ending Heimdall, also end the PID that `spawned` names, through a handle opened when the record was read and checked by identity. Alternatively, state the limit in the README and in `WINDOWS_HELD`.

### M07-W7-R04: low, nonblocking. Newest-first crediting (the M07-W6-R02 fix) can settle the wrong request on a guess.

**Where.** `harness.py:1367-1379` (`together`, newest first) with `observed` (`:1599-1642`; `:1639` deletes a settled request). The text that overstates it is `README.md:589-596` ("What the list cannot settle stays as it was").

**What happens.** Take two remembered silent requests, R1 then R2, for the same work and profile. The list shows one binding whose `created_at` is after R2 was sent. R1 can make such a binding, for example when its operation is slow. H2 credits the binding to R2 (`binding_found`), releases it, and stops observing R2. R1 stays `still_unknown`. If R1 did make that binding, R2's own operation is never looked at again, and a binding it makes later is not released.

**Reproduced** with `probe/p_r02.py`, using the shipped harness and the suite's own stub in mode `work:binding_many_late/made-2:active`. Calls: `inspect bindings`, `access release binding_many_late`, `inspect bindings`. R2: `unanswered`, then `binding_found`. R1: `unanswered`, then `still_unknown` in the stop and again in the close. Exit 1. The control `made-1` credits R1 correctly.

**Why nonblocking.** The binding released passes every ruled attribution check for R2, and it is one of H2's own requests' bindings. The run exits 1. This is the U0-Q7 residual: no field names the request.

**Smallest fix.** When an older, still-uncertain request for the same work and profile was sent before the candidate's `created_at`, release the binding but keep both requests uncertain, recording `candidates`. Alternatively, document this case beside the two-bindings case in the README.

### M07-W7-R06: nit. Two oracles are weaker than stated.

**(a) The sidecar's forbidden-option check misses a leading space or a quoted keyword.** `option_name` (`pinned_ssh.rs:276-282`) takes the text before the first `=` or whitespace. So `" User=other"` is named `""` and `"\"User\"=other"` is named `"\"user\""`, and neither matches FORBIDDEN (`:578`).

OpenSSH skips leading whitespace in a keyword: `ssh -G -o " User=other"` printed `user other`. Reproduced with the built wrapper: a sidecar with `" User=other"` started the client, with exit 0 and the option passed through. `"User=other"` was refused with exit 125. The `-G` guard covers the identity keys this way, but not `HostName`, `User` or `Port`. The sidecar is test-authored.

**Fix:** trim and unquote before naming the option, or refuse an option whose first character is not an ASCII letter.

**(b) The marker in `release-gate.sh:231-245` cannot appear even if the gate regressed.** In an empty scratch home, `connect alpha` stops at the unknown destination (`crates/heimdall/src/connect_cmd.rs:155-161`) before any launch. The exit-2 and refusal-text check is the real oracle, and it passed. ADR-0007 §12.52 item 1 ("the probe fails if the marker appears") should say the marker is a backstop only.

## Checked and clean

**H2 (M07-W6-R01 to R03 closure).**
- *R03, never exit 0 while uncertain.* Read from source. `exit_status` (`harness.py:2098-2105`) fails the run when any request attempt exists (`by_request` lists every `asked` entry), any release attempt did not release, anything is held, or `requests`/`uncertain` is non-empty. I traced every path that ends a goal while a request is uncertain, and each records an `asked` attempt:
  - `leave_open` on every PlannerError/OSError out of `steps`, and in the expected-refusal branch;
  - `uncertain_answer` for an `OUTCOME_UNKNOWN` answer that reaches no TRACKED state;
  - `unresolved` at the bound in `reconciling`;
  - the IN_FLIGHT bound row.

  An expected refusal is met only when it is not `OUTCOME_UNKNOWN`, the request is not unanswered, `leave_open` found nothing open, and the request is not remembered. `REQUEST_SAYS` settles a watched answer only on a succeeded view naming a binding, or a terminal failed or cancelled view with effect `none`. A refusal envelope of the wait itself (no `data.state`) stays open. No path I found exits 0 with something uncertain.
- *R01.* The step limit in `observing` and `pending_approval`, a transient wait refusal, a no-answer wait in all three TRACKED states, a wait in the wrong exit class, an operation whose own code is `OUTCOME_UNKNOWN`, and an abandoned handoff: each is remembered with its operation and observed by the close or a later stop. This holds by source, and the suite covers it (`test_an_answered_request_whose_operation_is_still_open…`, `test_the_other_requests_left_open…`).
- *No resend after `OUTCOME_UNKNOWN`.* The only `REQUEST` re-sends come from FOLLOW states reached before any uncertain answer (`pending_provider`). TRACKED states only wait.
- *R02.* Each binding is credited to at most one request: `ever_held` is filtered in `observed`, in `together`'s order. Requests that named an operation are observed first. Two late candidates mean `SEVERAL`, so nothing is released. The probe control `made-1` attributes correctly. The guess is R04.
