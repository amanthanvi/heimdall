### M07-W9-R03: `open_pipe` waits once more after its last try

- **Severity:** nit.
- **Blocks under §2.1:** no. It is test-only code and fails closed.
- **Evidence:** in `crates/testkit/src/win.rs:476-500`, the loop runs `0..=PIPE_BUSY_RETRIES`
  (six tries). Each busy try then calls `WaitNamedPipeW` for up to `PIPE_BUSY_WAIT_MS` (2 s),
  including after the sixth try, before `WouldBlock` is returned. That adds up to 2 s to a
  refusal and has no effect on correctness. The `WaitNamedPipeW` result is ignored, which is
  fine because the next `CreateFileW` decides.
- **Fix:** skip the wait on the last iteration, or loop on `1..=PIPE_BUSY_RETRIES` with the wait
  in between.

### M07-W9-R04: the release gate never probes the TUI's own hooks (existed before W9; W9d makes it cheap)

- **Severity:** nit (gap in an existing check).
- **Blocks under §2.1:** no. The code refuses both hooks in release (`test_hooks` calls
  `testcfg::refusal(testcfg::AVAILABLE, true)`), so no trigger exists.
- **Evidence:**
  - `HEIMDALL_TEST_TUI_SCREEN` and `HEIMDALL_TEST_TUI_PANIC` (`crates/heimdall/src/tui/mod.rs:78`
    and `:83`) are not in `LAUNCH_ENV` or `ALL_ENV`, so `tools/validation/release-gate.sh`
    (`read_vars`, lines 89-104) never probes them.
  - Their only test, `tui::tests::the_test_hooks_are_parsed_in_debug_and_refused_in_release`,
    runs its release branch only in a release test build. `grep -n -- --release

## What I found sound

### Q1, W9d: the TUI honours the debug-only redirect

- **Unreachable in release.** `testcfg::launch_hooks` refuses any `LAUNCH_ENV` variable when
  `AVAILABLE` (`cfg!(debug_assertions)`) is false. `PINNED_CLIENT_ENV` is in `LAUNCH_ENV`
  (`testcfg.rs:107-115`, `:205-212`). So in a release build `hooks.pinned_client` is always
  `None`, and `connect(…, None)` follows the product path unchanged.
- **Refused before anything else.** The TUI now calls `launch_hooks` and `test_hooks` before the
  `--json`, terminal and home checks (`tui/mod.rs:205-215`). Both entry points, `heimdall tui`
  and the bare TUI (`cli.rs:1639`, `:1693`), call this one `run()`.
- **Observed here:** the release gate passed on `c71bbd76` (52 probes, 0 failed). Every
  `tui (no terminal)` probe passed, with exit 2 and the refusal text.
- **The release-gate probe tells the two outcomes apart.** A build that ignored the variable would
  stop at "the TUI needs a terminal…". That message matches neither `HEIMDALL_TEST_` nor
  "test configuration", so the probe fails (`release-gate.sh:174-181`, the `grep` for the refusal text).
- **Only an explicit variable triggers it.** The redirect comes only from
  `std::env::var_os("HEIMDALL_TEST_PINNED_CLIENT")`, which must be an absolute path. Nothing
  derives it from configuration, the runtime or any other source.
- **Same as `heimdall connect`.** The TUI replaces only the program path
  (`tui/mod.rs:511`; compare `connect_cmd.rs:157`). The single alias argument, the empty
  `EnvDelta` and the handoff are unchanged. Neither path guards against a missing redirect on
  Windows; both rely on the AGENTS.md rule.

### Q2, W9e: the declared-pipe check

**Which pipes can pass.** A pipe passes only if it meets all of these:

- the name rule;
- an exact `SSH_AUTH_SOCK` match;
- a server PID and creation time equal to what the sidecar declares.

The cases I checked:

- **The system agent pipe** fails the `heimdall-` prefix rule.
- **The M04 session-agent pipe** (`\\.\pipe\heimdall-<32 hex>`, `credential/src/mgmt/agent.rs:56`)
  has no `<token>-<kind>`, so it is refused.
- **Control and issuer pipes** are refused in any case. Win32 trailing-dot normalisation is
  closed by refusing a trailing `.`. Spaces, separators, `%`, non-ASCII, and the `//./`, `\\?\`
  and `\\server\` spellings are refused (`the_declared_agent_pipe_name_rule`).
- **Pre-created decoy or squatter.** The fixture agent's first instance is created with the
  first-instance flag and a protected owner-only DACL (`testkit/src/agent.rs:577-585`, via
  `heimdall_ipc::windows::Listener`). A name taken in advance makes the fixture's bind fail; it
  cannot produce a pass. The name holds a random hex token, and another account cannot add an
  instance.
- **A reused PID** fails the creation-time comparison.
- **A server that exits** between `GetNamedPipeServerProcessId` and `OpenProcess` gives an error
  or a different creation time, so the wrapper refuses.
- **A same-user process adding an instance** after the check is the stated check-then-use
  residual (`pinned_ssh.rs:182-184`). It falls under ADR-0009 §2.1's same-user (P03) rule, and
  it gains such a process nothing beyond what it could already do. Its only effect would be to
  answer the test's ssh with its own keys.

**The check-then-use window in a test context.** Not exploitable beyond P03. The test process
serves the pipe for its whole life, and no other account can create an instance.

**The `unsafe` code** (`win.rs:419-549`) is sound:

- Names are NUL-terminated (`wide` refuses an embedded NUL) and outlive each call.
- `CreateFileW` uses `OPEN_EXISTING` and `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`.
- A returned handle is wrapped in an `OwnedHandle` at once, with both `INVALID_HANDLE_VALUE` and
  null guarded. It is dropped on every early return (`GetFileType` ≠ `FILE_TYPE_PIPE`, or
  `GetNamedPipeServerProcessId` failing) and dropped explicitly on success.
- `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` is null-checked and owned.
- The `FILETIME` out-pointers and the `&raw mut pid` out-pointer are valid locals.
- No buffer sizes are involved. The 64-bit creation time is assembled as high << 32 | low.

**Refusals.**

- **Without a declaration** nothing changes: `identityagent` values such as `SSH_AUTH_SOCK`,
  `$…` and `%…`, the system pipe, and pipes that are not fixture pipes are still refused
  (`check_effective`, `pinned_ssh.rs:886-903`; `guard_refuses_the_system_agent_pipe`; the last
  block of `a_declared_agent_pipe_is_accepted_only_from_its_runtime`).
- **With a declaration**, `-o IdentityAgent=//./pipe/<name>` is placed right after `-F`, ahead of
  the caller's words. Because the first value wins, neither a caller `-o IdentityAgent=…` nor a
  projected block can replace it.
- **A build that cannot read a server** (any build without Windows and `fixtures`) refuses a
  declared pipe (`the_built_wrapper_refuses_a_declared_pipe_it_cannot_check`, run here).

**Could a misconfigured test reach the owner's real agent?**

- **The system agent (`openssh-ssh-agent`):** no. It is refused in every mode, by name, and
  separately by PID: the SYSTEM service is never the declared process.
- **A real Heimdall runtime's `-signing` or `-b<hex>` endpoint:** this passes the name rule. The
  wrapper alone cannot tell a scratch runtime from a real one; it trusts the PID its sidecar
  declares.
  - The A32 driver closes this gap. It requires the binding's `SSH_AUTH_SOCK` to equal the lab
    agent's endpoint, and `service status`'s PID to equal `std::process::id()`
    (`harness_m07.rs:993-1056`), before it declares anything.
  - The PC also had no Heimdall install (`localappdata-heimdall-before=absent`).

### Q3, W9b: the TUI reader for `noninteractive`

- **Every shape reads correctly.** The emitter (`app/src/operations.rs:5698`, `identity_view`)
  always sends `PairEligibility.noninteractive`, which is the contract type
  `NoninteractiveEligibility` (`domain/src/catalog.rs:590`).
- **Absent, unknown and old shapes fail safe to "unknown".** The reader takes `.eligible` as a
  boolean, so these all read as `None` ("unknown"):
  - absent;
  - `null`;
  - the old bare boolean;
  - an object without `eligible`;
  - a non-boolean `eligible`.
- **Display only.** The value appears in only three places in the TUI (`m07.rs:388`, `:456`;
  `view.rs:2182`), so there is no consent effect.
- **Test coverage.** The new test covers eligible, refused and absent. The other shapes need no
  new test under ADR-0009 §2.3.
