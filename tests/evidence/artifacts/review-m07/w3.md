**M07-W3-R01 — moderate — H2 does not release every binding it receives.**
`examples/harnesses/goal-loop/harness.py:579,604,661`; `tests/e2e/harness_m07.rs:1193–1217`.
After access succeeds, a later failed goal leaves the earlier binding in `held`, but `stop` accepts only `ready`/`running`; `close()` ends a child without releasing bindings. Independently, seven held bindings exhaust the six-step stop limit, leaving one binding in `releasing`, from which another stop is refused. The real fixture-adapter journey also ends its two successful access goals without a stop.
Probe: the shipped Python stub produced successful access → failed access → refused stop; `held=[binding_fixture]`, zero release calls after close. A seven-binding table probe released six, retained one, and refused another stop. A temporary native-test assertion confirmed **two active bindings** immediately after H2's fixture-adapter goals, while the complete journey still passed (exit 0). Allow cleanup from any state with held bindings, make bounded cleanup resumable, and stop/release the fixture-adapter bindings before recording completion. The README discloses the failed-goal limitation, but that does not satisfy the supplied release ruling.

**M07-W3-R02 — moderate — the login oracle bypasses the descriptor's authentication endpoint.**
`tests/e2e/wrapper_m07.rs:1118–1147`; the same pattern is in `tests/e2e/harness_m07.rs:685–724`.
The test checks the descriptor endpoint string, then disables agents and supplies the generated private key with `-i`. Thus SSH proves alias/config routing and fixture-key authentication, but does not prove that the endpoint returned by materialize can sign, or that the child uses that endpoint. A broken consumer signing endpoint can pass this oracle.
Probe: after materialize, I dropped the descriptor's `FakeAgent` and asserted that connecting to its socket failed; `materialize_log_in_and_release_through_the_wrapper` still passed (exit 0). Keep the current isolated login check, but add an endpoint usability/authentication assertion appropriate to the disposable fixture, or limit the evidence claim to routing plus direct fixture-key login. No owner key/agent was involved.

**M07-W3-R03 — low — H2 discards the CLI exit status.**
`examples/harnesses/goal-loop/harness.py:507–525`.
An `ACCESS_READY` envelope with an erroneous process exit 1 is counted as a successful goal, so H2's A32 success record cannot detect that CLI exit-contract regression. Unlike H1, it never examines `done.returncode`.
Probe: changed only the scratch stub's successful ensure to emit its usual envelope and actually exit 1; H2 recorded `success=true`, `ready`, one call (probe exit 0). Check the documented exit class as well as the envelope, including bounded-wait `ACCEPTED` and operation-observation exits.
