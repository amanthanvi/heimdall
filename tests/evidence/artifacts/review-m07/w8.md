## Findings

### M07-W8-R01: moderate, nonblocking. Once the shared binding is released, `contested` stops working. A later read then credits the older request's other candidate and releases it, and the run summary does not name it.

**Where.**
- `examples/harnesses/goal-loop/harness.py:1897-1898`. `could[other]` adds a contested binding only through `matching[other]`.
- `read_work` (`harness.py:1013`) puts only `active` bindings in `matching`.
- So a contested binding counts in a later read only while the list still names it `active`. The SHARED_FIND path itself makes that rare: the same stop releases the binding (`DEALT_WITH`, `harness.py:552`).

**The claims it contradicts.**
- `harness.py:1490-1493`: "A later read of the list still counts each as a candidate of those requests: it keeps that read ambiguous".
- `harness.py:1885-1887`: "so that no later read credits what an earlier one could not".
- `README.md:663-664`.
- The W8c paragraph of `docs/architecture/m07-plan.md:606`: "A binding held that way stays a candidate of those requests in every later read, so a later stop or the close never credits what an earlier read could not".
- Ruling 2 (later reads), and ruling 3: a binding H2 cannot attribute and never held stays active and is named in the run summary.

**What happens (A15, the suite's own case, but with a list that shows a release).**
- R1 is sent, then R2, both silent, for the same work and profile.
- `binding_second` is made between the two sendings, and `binding_many_7` after both.
- **Read 1 (the stop)** is ambiguous:
  - R1 has two candidates and R2 has one;
  - `binding_many_7` is held, contested and released;
  - `binding_second` is unattributed.
- **Read 2 (the close)** no longer lists `binding_many_7` as `active`, because it was released:
  - `could[R1] = {binding_second}` and `could[R2] = {}`, so nothing is shared;
  - R1 gets `found = one`, then `binding_found`;
  - `binding_second` is held and released, and R1 is settled.
- `left_active` ends up empty, because the binding is now in `ever_held`.

Read 1 had established that R1 may have made `binding_many_7`. In that case `binding_second` is not R1's, so H2 released a binding ruling 3 says must stay active and be named.

**Reproduced.** `probe/p1_later_read.py` replays the suite's A15 `stop` row (two silent `access` goals, then a stop goal, then the close) against the suite's own `STUB`. One change makes a released binding listed `released` afterwards, as `inspect bindings` would list it.
- **Live list:**
  - calls after the requests: `inspect bindings`, `access release binding_many_7`, `inspect bindings`, `access release binding_second`;
  - R1 attempts `unanswered`, `still_unknown` (candidates both, `shared_with` R2), then `binding_found` (bindings `binding_second`, by the close);
  - only R2 is left uncertain, `left_active` is `[]`, and the exit status is 1.
- **Control:** with the unchanged static stub (`p1_later_read.py <wt> static`) the suite's behaviour holds. `binding_second` is never released, and `left_active` names it.

**Why the suite misses it.** The stub's `work:` mode lists every binding as `active` whatever was released (`test_harness.py` STUB `:359-362`). The A15 `stop` assertion `assertNotIn(["access", "release", one], after)` (`test_harness.py:3441`) holds only because of that. The `no-contested` mutation (below) shows the test does exercise `contested`, but only in a world where a release is never seen.

**The same pattern without SHARED (inference, source only; behaviour from before W8).** A request alone with two candidates (SEVERAL) is credited in a later read if one of them has gone from the list (expired, or released by someone else).

**Why nonblocking.** The binding released passes R1's attribution checks. A binding release is not remote trust, a recovery record or the owner's data. The run still exits 1, because R2 stays uncertain and `by_request` is non-empty. H2 is a fixture-only example.

**Smallest fix.** Make the memory independent of the list:
- keep, for each contested binding, the requests it was a candidate of (`self.contested[binding] = set(requests)`);
- add it to `could[other]` whenever `other` is in that set, whether or not `matching` names it.

An equivalent fix: a request observed in an ambiguous read is never credited later (`found = withheld`). Add the A15 `stop` row with a stub list that shows a released binding as `released`.

### M07-W8-R02: low, nonblocking. A remembered request that named an operation is not a peer in the list read. A silent request is credited with a binding that request may have made.

**Where.**
- `together` (`harness.py:1655-1667`) includes only requests that named no operation.
- `conclude` (`:1889-1906`) judges ambiguity only among those.
- `README.md:651-652` says the operation-first order means "the list never offers a binding their operation names to another request". That holds only when the operation's observation names the binding.

**What happens.**
- R-op (sent first, operation `op_peer`) and R-silent are both remembered for the same work and profile.
- In the stop, R-op's wait is refused for now (`STATE_UNAVAILABLE`, `retry_after`, exit 5). Its reading is `still_unknown`, so that operation may have succeeded.
- The list names one `active` binding, made after both sendings.
- `binding_x` is credited to R-silent (`binding_found`, no `shared_with`) and released, and R-silent is settled.

Ruling 2 says a read that "cannot tell which remembered request made a binding" credits none. If R-silent later makes its own binding, nothing observes it and `left_active` does not name it.

**Reproduced.** `probe/p2_op_peer.py` uses a minimal stub. The remembered state is set as `remember` leaves it.
- Calls: `operation wait op_peer`, `inspect bindings`, `access release binding_x`, then the close's `operation wait op_peer`.
- Attempts: R-op `still_unknown` twice; R-silent `binding_found`.
- `left_active` is `[]`, and the exit status is 1.

**Status.** This dates from M07-W6-R02, not from W8. W8 did not narrow it, although the strict reading covers it.

**Why nonblocking.** The binding released is one of H2's own requests' either way, and the run exits 1.

**Smallest fix.** Count each still-uncertain request of the same work and profile that named an operation as a peer in the read:
- its attribution matches go into `could`;
- it is never credited from the list.

Alternatively, state the limit in the README beside the U0-Q7 note.

### M07-W8-R03: low, nonblocking. An answer whose typed field is present but invalid misses ruling 4's fail-closed path. This is broader than the item already carried.

**Where.**

**Reproduced** with `probe/p3_bad_field.py` (a minimal stub, one `access ensure` per case, then the close):

## Checked and clean

**R03, the Windows child.** Read from source, with job 52's run.
- **Never by name.** Every termination goes through a handle opened by PID (`WindowsProcesses.open`), and none goes through a name or a snapshot.
- **The order of checks.** H2 opens the PID the record names before anything else is read of the launch, then checks it in this order:
  - **Parent:** the parent must be the PID of the `heimdall.exe` H2 started, read from the snapshot while H2 holds the child's handle;
  - **Creation time:** it must be created at or after that `heimdall.exe`;
  - **Image:** the image must be the goal's program by real path, or `System32\cmd.exe` for a batch script.
- **PID reuse between the record and the open.**
  - While Heimdall runs, it keeps the child's handle (`crates/launch/src/windows.rs:78-89`: the `std::process::Child` is held across `wait`), so the PID cannot be reused.
  - After Heimdall has gone, H2's Popen handle still pins Heimdall's PID. A recycled PID's process therefore cannot have Heimdall's PID as its parent unless Heimdall created it.
  - The image check excludes the runtime that Heimdall may start on demand.
- **Fail-closed paths.** A running process that fails a check, or cannot be opened or read, is left alone, and the launch fails (exit 1). An exited child is not held.
- **Ending.** `Spawned.end` runs once, terminates and then waits within the bound, and closes its handle on every path. `Child.end` waits for a natural exit first, then ends the held child before terminating Heimdall. A stop with `not_ended` fails, and so does a close with `not_ended` (`exit_status`).
- **The ctypes layer** matches the Win32 definitions:
  - the `PROCESSENTRY32W` layout;
  - the access mask: QUERY_LIMITED, TERMINATE and SYNCHRONIZE;
  - the `INVALID_HANDLE_VALUE` compare;
  - error 87 read as "no such process".

  Job 52 ran the real kernel32 path. The goal-loop suite there ran 107 tests and passed, the Windows test included. `e2e_harness_m07` passed 5 of 5, with A32 asserting `held: true` and `ended: exited, exit_code 0`.
- **Ruling conformance (for the contract owner).** The ruling allows a job object "if the record cannot give a start time". The record gives none. Instead H2 checks creation against Heimdall's start, with the parent check. `m07-plan.md:606` (W8a) gives the reason: a kill-on-close job without breakaway would end the runtime that `heimdall run` may start. By source this is as strong as a start-time check for the PID-reuse threat. It is a deviation from the fallback clause, documented, and not a defect.
- **Narrow, not probed (inference).** Suppose the child is up, H2 has not seen `spawned` within `SPAWNED_SECONDS`, and Heimdall writes it just before H2 terminates Heimdall. Then the child is not held. The goal fails anyway.

**R04, the strict reading, within one read.**
- When any binding is a candidate of two requests, no request is credited: WITHHELD, SEVERAL and SHARED_FIND all mean still unknown.
- A shared single candidate is held and released.
- Every request stays in `requests`, so `by_request` is non-empty and the exit status is 1.
- Candidates are taken before anything in the read is held.
- `made-1` is credited correctly.
- This holds by source and by the suite. The only gaps are across reads (R01) and with operation-named peers (R02).

**Ruling 3.** The format of `left_active` matches the ruling. Bindings that are not candidates (another work, made before the request was sent, a foreign profile) are never named or released. The `exit_status` clause for `left_active` cannot change the result: every unattributed binding comes from a list observation that also appends to `asked`, so `by_request` is already non-empty.

**Ruling 4** holds for missing fields, unknown codes, `UNSUPPORTED_CLIENT`, an unpaired action (`odd`) and exit-class mismatches.
- A mismatch ends in `inconsistent` with `listed` false, and the request is remembered.
- Nothing is re-sent: the goal ends at that answer. `pending_provider` is the only resend path, and no uncertain answer reaches it.
- The close observes the request by its operation, else through the list.

The gap is invalid fields (R03).

**Ruling 5.**
- `FOR_NOW` equals the class-5, retryable, `retry_after` codes of `schemas/public-api/codes.json`. I checked that independently: DESTINATION_UNREACHABLE, TIME_UNCERTAIN, SERVICE_UNAVAILABLE, STATE_UNAVAILABLE and BACKPRESSURE. UNSUPPORTED_CLIENT is excluded (`change_client`, not retryable).
- Each `TRACKED` state ends in `failed(code, operation_id, request_id)`.
- `leave_open` remembers the request as `still_unknown`, since the refusal has action `retry_after`, not `none`, so it can never read NEVER_RAN.
- The PS1 observation lines only call `Add-Fact` and the build-log append. No `$overall` assignment reads them, and the build-failure `throw` does not test `$pinned`. Job 52 shows `other-keys-offered-a01=0` and `a11=0` in `host.txt`, and the `hm-pinned-ssh.exe` digest in `build.txt`.

**No exit 0 while anything is uncertain.** Every new outcome records an `asked` attempt (`kept`, `observed`) or fails a goal:
- UNLISTED;
- SHARED_FIND;
- WITHHELD;
- `not_ended`.

**The case index.** The JSON parses. All 24 test patterns it names resolve to an existing `fn` or `mod` in their Cargo target. The only status used is `blocked`; see R06(a).

**The design note** (`m07-plan.md`, the routed Windows row) is design only and changes no code.
