### Legitimate states and platform differences

- **Missing quarantine, existing valid parent:** accepted with `Ok(None)`; nothing is created.
- **Missing parent:** the SSH user check (`plan.rs:874`) and Git check (`git.rs:57`) retain their early missing-directory allowance. The P/key check still leaves an unopenable directory to apply. The helper therefore does not turn ordinary first adoption into manual mode.
- **Quarantine mode repaired by its creator:** `sys/quarantine.rs:233` repairs a *freshly created quarantine's* narrowed mode before validation. Preview still accepts an absent quarantine, so that later apply repair remains reachable. An already-existing invalid quarantine is deliberately refused, as before; preview never repairs it.
- **Directory permissions changed after opening:** `still_valid` compares identity, current validity, and exact permission bits (`replace.rs:242`). Even a valid-to-valid Unix mode change such as 0700 to 0755 now refuses this preview check. This is the expressly requested parity with `open_or_create`, a conservative retry/manual outcome, not data loss. Apply creates missing parent directories before opening their handles (`apply.rs:1057,3172`); this change does not insert a later writer chmod of the same parent that would invalidate a legitimate preview handle.
- **Windows:** `still_valid` reads metadata from the existing pinned directory handle, not a reopened user path. Windows metadata has `perm: 0` (`sys/quarantine.rs:1482`), so Unix mode comparisons do not impose a Windows DACL condition. Identity, directory/reparse status, and owner are rechecked. Existing quarantine DACL validation remains in `open_existing_at`. No Windows creation or sharing-policy change was introduced.
- This is a point-in-time check, not a promise that metadata cannot change immediately afterward. Apply retains its own checks. No race was executed in this review.
