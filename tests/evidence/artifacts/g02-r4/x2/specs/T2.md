# X2 task T2: new subcommand `heimdall-proto profile lint`

**Task type:** new CLI subcommand.
**Applies to:** the `heimdall-proto` prototype in your workspace. Change only that prototype.
**Workspace:** your workspace has the layout of the project repository, reduced to what this task
needs: the prototype under `prototypes/`, `docs/g02/slice-contract.md`, `schemas/g02/`, the G02
harness in `tests/g02/` (with its pyte venv in `tests/g02/.venv`) and the fixtures in `tests/fixtures/`.
Paths in this spec are relative to the workspace root. Work only inside the workspace.

## Summary

Add the subcommand

```
heimdall-proto profile lint --file <path> [--json]
```

It reads a profile in the same way as `profile show` and reports findings about a profile that is
schema-valid. The options may be given in either order. Everything that the slice contract
(`docs/g02/slice-contract.md`) says about `profile show` input handling also applies to `lint`.
This covers §1, §2, K2, K12, K14, K15 and K18.

## Input handling (same as `profile show`)

If `profile show --file <path> --json` would fail, `profile lint --file <path> --json` fails in the
same way. Its exit status, `state`, `code` and `data.error.key_path` are the same as those of
`profile show`. Examples: SCHEMA_INVALID, INPUT_TOO_LARGE, and USAGE_ERROR for a missing file,
directory or FIFO (K14: never blocks, answers within 2 s). Usage errors follow §1: a missing
`--file`, a flag without its value or an unknown flag exits 2, with a `USAGE_ERROR` JSON result on
stdout only when `--json` is given.

## Rules

Lint applies only to destinations. `name`, `revision` and `[meta]` are never linted. The *effective
port* is `port`, or 22 when `port` is omitted. *ASCII-lowercase* means mapping `A`–`Z` to `a`–`z`
and leaving every other character unchanged.

| # | rule id | fires when | one finding per | `key_paths` | `message` (exact) |
|---|---|---|---|---|---|
| 1 | `duplicate-endpoint` | Two or more destinations have the same ASCII-lowercased `host` and the same effective port. | Group of such destinations. | `destinations[i].host` for each member, in file order. | `destinations share the same host and port` |
| 2 | `privileged-port` | The effective port is below 1024 and is not 22. | Destination. | `destinations[i].port` | `port below 1024 other than 22` |
| 3 | `root-account` | `account` is exactly `root` (case-sensitive). | Destination. | `destinations[i].account` | `account is root` |
| 4 | `duplicate-label` | Within one destination, the same label string (exact comparison) occurs more than once. | (Destination, label string). | `destinations[i].labels[j]` for every occurrence `j` of that string, ascending. | `label repeated within a destination` |
| 5 | `label-case-variant` | Across the whole profile, two or more *different* label strings are equal after ASCII-lowercasing. | Set of labels that are equal after ASCII-lowercasing. | `destinations[i].labels[j]` for every occurrence of every spelling in the set, ordered by `(i, j)`. | `labels differ only in letter case` |

Indexes `i` and `j` are zero-based positions in the file. Paths use exactly the form
`destinations[2].labels[0]`.

A label string that is identical in two destinations is not a finding. Two labels in the same
destination that differ only in letter case are a rule 5 finding and not a rule 4 finding.

## Finding object and order

Each finding is a JSON object with exactly these four members:

```json
{"rule": "<rule id>",
 "key_paths": ["destinations[0].host", "destinations[3].host"],
 "destination_ids": ["<id of each destination named in key_paths, first-appearance order, no repeats>"],
 "message": "<the exact message from the table>"}
```

Findings are ordered by rule number (1 to 5). Within one rule, the order is as follows.

- Rule 1: by the index of the group's first member.
- Rules 2 and 3: by destination index.
- Rule 4: by destination index, then by the index of the label string's first occurrence.
- Rule 5: by the `(i, j)` of the set's first occurrence.

## Result

On a schema-valid profile, the output with `--json` is exactly one JSON document followed by
`\n`. It uses the existing result envelope (§1):

```json
{"schema_version": "1", "state": "succeeded", "code": "LINT_CLEAN" | "LINT_FINDINGS",
 "data": {"findings": [ ... ]}, "warnings": [], "next": null}
```

| outcome | `code` | exit status |
|---|---|---|
| no findings (`findings` is `[]`) | `LINT_CLEAN` | 0 |
| at least one finding | `LINT_FINDINGS` | 3 |

`data` has no members other than `findings`. JSON member order does not matter. The order of the
`findings` array, and of the arrays inside each finding, does matter. The new codes are not in
`schemas/g02/result.schema.json`. Do not edit `schemas/`. The envelope shape is unchanged.

Without `--json`, the output is unspecified and not judged (K12). The exit status is the same as with
`--json`.

## Value non-echo

Profile values are not printed on stdout or stderr, with or without `--json`. This covers `name`,
`alias`, `host`, `account`, labels and anything in `[meta]`. Findings name places by key path. The
only values that may appear are destination `id`s, in `destination_ids`. For errors, K18 applies
unchanged.

## Acceptance

Black-box tests, which you will not see, run `profile lint` on darwin-arm64 and linux-arm64. They
use fixture profiles that trigger every rule and its near misses, and they compare the exact
expected JSON: envelope, `code`, `data`, and the order of findings. They also check exit statuses
with and without `--json`, both option orders, paths with spaces and non-ASCII characters, and
equivalence with `profile show` on invalid and non-regular inputs. Finally, they check that no
profile value appears on stdout or stderr, that the usage errors behave as stated, and that no file
is written. The full 2.4.2 harness and the prototype's own unit tests are run as well.
