**Task type:** interactive TUI feature.
**Applies to:** the `heimdall-proto tui` of the prototype in your workspace. Change only that

**Workspace:** your workspace has the layout of the project repository, reduced to what this task

harness in `tests/g02/` (with its pyte venv in `tests/g02/.venv`) and the fixtures in `tests/fixtures/`.
Paths in this spec are relative to the workspace root. Work only inside the workspace.

Three changes to `heimdall-proto tui --file <path>` (`docs/g02/slice-contract.md` §5). Everything
in §5 and its clarifications (K10, K16, K17) still holds, except K9, which part C replaces.

## A. Highlight the matched text

While the filter text is not empty, the matched text is underlined in every list row on screen. This
applies both in filter mode and after `Enter` has left filter mode with the filter kept.

- In the alias, the characters of the first case-insensitive occurrence of the filter text are
  underlined.
- When the row also shows the host (terminal width of 50 columns or more), the characters of the
  first case-insensitive occurrence of the filter text in the host are underlined too.
- A row that matches only through its host has only that part underlined.
- No other cell of a list row is underlined. This includes the `> ` prefix, the separators, the
  account, `@`, `:`, the port, and any later occurrence of the filter text.
- When the filter is empty, for example after `Esc` clears it, no list cell is underlined.
- "Underlined" means the terminal underline attribute (SGR 4, or an equivalent underline form).
  Underline is not a colour, so it is also shown when `NO_COLOR` is set, and `NO_COLOR` must still
  produce no colour SGR at all.
- Case-insensitive matching is the same rule the existing filter uses. The tests use only ASCII
  letters and CJK characters, so lowercasing never changes the length of a string.

## B. Help overlay

- When not in filter mode, `?` opens a help overlay. In filter mode, `?` is ordinary filter text.
- While the overlay is open, these nine lines are on screen. Each is on its own row, in this order
  from top to bottom. The comparison ignores leading and trailing spaces and treats any run of
  spaces as one space. The lines may be framed or indented.

  ```
  Keys
  Up / k      move up
  Down / j    move down
  /           filter
  Enter       select
  Esc         clear filter
  q           quit
  ?           close help
  Ctrl-C      cancel
  ```

- `?` or `Esc` closes the overlay. Here `Esc` only closes it and does not clear an active filter.
- While the overlay is open, every other key is ignored, except `Ctrl-C`. `Ctrl-C` cancels as it
  does elsewhere: the terminal is restored and the exit status is 130.
- After the overlay closes, the list, the filter text, the filter state and the selection are the
  same as before it opened. None of the help lines remains on screen.
- At small sizes (down to 20x5) the overlay may be clipped, but opening it, resizing and closing it
  never crashes.

## C. Selection kept across filter edits (replaces contract K9)

A filter edit is an appended character, `Backspace`, or the `Esc` clear in filter mode. After a
filter edit:

- If the destination that was selected just before the edit is among the rows now shown, it stays
  selected. The list scrolls if needed so that it stays visible.
- Otherwise the first shown row is selected. This includes the case where no row was shown before
  the edit.
- Leaving filter mode with `Enter` keeps the selection, as before.

`Enter` outside filter mode still selects the marked destination and prints
`SELECTED <alias>`.

## Constraints

- **The full G02 harness 2.4.2 must still pass,** both on darwin-arm64 (`tests/g02/conformance.py`)
  and on linux-arm64 (`tests/g02/linux/run.sh`), with three exceptions. These three checks encode
  or assume the K9 rule that part C replaces, so a correct implementation fails them:
  - `tui.filter_edit_resets_selection` checks K9 itself.
  - `tui.no_color`: its last step expects the first row to be selected after `Esc` clears a filter
    that had left another destination selected.
  - `tui.large_100_filter_latency`: its update predicate expects the list to start at the first
    match after every filter edit.

  All other 136 checks must pass, including the resize, tiny-terminal and exit-path checks. The
  remaining requirements of the two incidental checks still apply, and the acceptance tests judge
  them:
  - With `NO_COLOR` set there is no colour SGR, and the selection is never shown by colour alone.
  - K17: on `large-100.toml`, the p95 keystroke-to-screen-update latency in filter mode is at most
    100 ms. An update counts when the status shows the new count, the list shows a full window of
    consecutive matching rows in profile order, and the `> ` marker is on the destination that part
    C selects.

  Unit tests in the prototype must pass. Update tests that assert K9 so that they assert part C.
- `build.sh` must still build every target it built before.
- Do not edit `docs/`, `schemas/`, `tests/g02/` or the fixtures.

## Acceptance

Black-box tests, which you will not see, drive the TUI in a pseudo-terminal with a terminal
emulator on darwin-arm64 and linux-arm64. They use `tests/fixtures/g02/profiles/homelab.toml` and
`large-100.toml` at 80x24, 40 columns and 20x5. They check the following:

- which screen cells are underlined, for single-character, multi-character, mixed-case and CJK
  filters, in filter mode, after `Enter`, after `Esc`, below 50 columns and with `NO_COLOR` set;
- the help lines and their order, and how `?`, `Esc`, other keys and `Ctrl-C` behave while the
  overlay is open;
- `?` in filter mode;
- the selection marker after each kind of filter edit, including a destination far down the
  100-destination list;
- the K17 latency measured as described above (5 filter sessions of 6 edits each);
- the `SELECTED` line and the exit statuses.

The full 2.4.2 harness and the prototype's own unit tests are run as well.
