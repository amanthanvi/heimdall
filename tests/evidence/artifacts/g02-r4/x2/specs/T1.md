# X2 task T1: exec-equivalent job control for `heimdall-proto run`

**Task type:** behaviour change in an existing subcommand.
**Applies to:** the `heimdall-proto` prototype in your workspace. Change only that prototype.
**Workspace:** your workspace has the layout of the project repository, reduced to what this task
needs: the prototype under `prototypes/`, `docs/g02/slice-contract.md`, `schemas/g02/`, the G02
harness in `tests/g02/` (with its pyte venv in `tests/g02/.venv`) and the fixtures in `tests/fixtures/`.
Paths in this spec are relative to the workspace root. Work only inside the workspace.

## Background

`heimdall-proto run [--meta-file <path>] -- <argv...>` starts a child program, waits for it, and
exits with the child's status (`docs/g02/slice-contract.md` §4 and §9). Under a job-control shell,
the user and the shell should not be able to tell the difference between `heimdall-proto run --
cmd` and running `cmd` directly. This is called *plain exec* below.

In five situations, the current program behaves differently from plain exec. This task is to make
it behave like plain exec in each of them, on darwin-arm64 and linux-arm64, under both bash and
zsh, without breaking any existing behaviour.

## Terms

- **Plain exec**: the same command line with the `heimdall-proto run [--meta-file M] --` prefix
  removed, run in the same environment.
- **The child**: the process that `heimdall-proto` started.
- **The launcher**: the `heimdall-proto` process itself.
- **Third party**: a process that is neither the shell, nor the launcher, nor the child. It sends a
  signal to exactly one PID with `kill(2)`.
- **Interactive shell**: `bash --norc --noprofile -i` or `zsh -f -i` running in a terminal, with
  job control. A command typed at its prompt runs as a foreground job.
- **Stop notice**: the line the shell prints when a foreground job stops, for example
  `[1]+  Stopped ...` (bash) or `zsh: suspended ...` (zsh).

## Required behaviour

Each scenario is judged against plain exec in the same environment, on the same platform, with the
same shell. Where plain exec gives an exit status, the launcher must give the same one.

### S1. Non-interactive parent: a third party stops the child, then continues it

A program that is not a shell starts `heimdall-proto run -- <cmd>`. None of stdin, stdout or stderr
is a terminal. The launcher runs in a process group of its own that is not orphaned. While `<cmd>`
runs, a third party sends SIGSTOP to the child, waits 0.5 s, and then sends SIGCONT to the child PID
only. The same scenario is also run with SIGTSTP instead of SIGSTOP.

Required, as with plain exec:

- `<cmd>` runs to completion.
- The launcher exits with the child's exit status within 6 s of the SIGCONT.
- The child is reaped. No zombie and no orphan is left.

### S2. Interactive shell: a third party stops the foreground child, then continues it

`heimdall-proto run -- <cmd>` runs as the foreground job of an interactive shell. A third party
sends SIGSTOP to the child, waits 0.5 s, and then sends SIGCONT to the child PID only. The same
scenario is also run with SIGTSTP.

Required:

- The shell prints a stop notice. `$?` at the shell's next prompt is the same as with plain exec,
  which is 128 + the number of the signal that stopped the child on that platform. The stop is
  therefore reported with the same signal that stopped the child.
- The child is not killed. It is continued by the third party's SIGCONT and runs to completion.
- After that, one of the following holds:
  - (a) The job finishes on its own, as with plain exec. `jobs` then lists no stopped or running
    job.
  - (b) **Permitted deviation.** The shell keeps listing the job as stopped until the user types
    `fg`. `fg` then ends the job with the child's exit status, and no job remains. This is allowed
    because a launcher that has stopped itself to report the stop cannot run, so it cannot see the
    child being continued.
- The interactive shell keeps running. No launcher or child process is left behind.

### S3. The child stops itself, then only the launcher is continued

`heimdall-proto run -- <cmd>` runs as the foreground job of an interactive shell. The child stops
itself with `kill(getpid(), SIGTSTP)`, which is what OpenSSH's `~^Z` escape does. The shell prints a
stop notice. A third party then sends SIGCONT to the **launcher's** PID only. With plain exec the
same SIGCONT goes to the job's only process, the child.

Required, as with plain exec:

- The child resumes running. With plain exec, a resumed child that then reads from the terminal in
  the background is stopped by SIGTTIN, and the shell lists the job as stopped.
- The shell never lists the job as running while the child is stopped.
- A later `fg` gives the terminal back to the child. The child reads the next line typed, and the
  child's exit status becomes the shell's `$?`.

### S4. A nested interactive shell is suspended and brought back

An interactive bash or zsh runs `heimdall-proto run -- bash --norc --noprofile -i`. In the nested
shell, the user types `suspend`.

Required, as with plain exec:

- The outer shell prints a stop notice and its prompt, and keeps running.
- After `fg` in the outer shell, the nested shell has the terminal again and answers typed
  commands.
- `exit 3` in the nested shell makes the outer shell's `$?` equal to 3.

### S5. SIGSTOP of the child, with `--meta-file`

`heimdall-proto run --meta-file M -- <cmd>` runs as the foreground job of an interactive shell. The
child is then stopped by SIGSTOP, in one of two ways: the child sends SIGSTOP to itself, or a third
party sends SIGSTOP to the child's PID.

Required, as with plain exec:

- The shell prints a stop notice, and `$?` is the same as with plain exec (128 + SIGSTOP's number
  on that platform).
- The child stays stopped, and the launcher stays alive, until the user types `fg`.
- After `fg`, the child reads from the terminal again.
- When the child then exits with status 0, `$?` is 0 and `M` holds `code` `CHILD_EXITED` with
  `data` `{"launched": true, "exit_code": 0, "signal": null}`.

## Constraints

- The slice contract `docs/g02/slice-contract.md` remains binding. This includes §4 (exit status
  128+N when the child dies by signal N, signal forwarding, no zombie or orphan), K5, K6, K6a–K6e,
  K16 (no other program is executed) and §9.4/§9.5. Where an earlier ruling only recorded one of
  the S1–S5 situations without gating it, this task now makes it a requirement.
- **The full G02 harness 2.4.2 must still pass:** all 139 checks of `tests/g02/conformance.py` on
  darwin-arm64, and all 139 under `tests/g02/linux/run.sh` on linux-arm64. Unit tests in the
  prototype must pass.
- `build.sh` must still build every target it built before, including windows-x64. The Windows
  code path must at least compile.
- Do not edit `docs/`, `schemas/`, `tests/g02/` or the fixtures.

## Acceptance

Black-box tests, which you will not see, run S1–S5 with plain exec as the control in the same
environment. They cover bash and zsh for S2–S5, SIGSTOP and SIGTSTP for S1–S2, and both triggers
for S5, on darwin-arm64 (host) and linux-arm64 (the container used by `tests/g02/linux/run.sh`).
Only observable behaviour is judged: shell output (stop notices, `$?`, `jobs`, prompts), process
states and reaping, exit statuses, the meta file, and whether typed input reaches the child. The
full 2.4.2 harness and the prototype's own unit tests are run as well.
