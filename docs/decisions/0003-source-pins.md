## Method (v2, reproducible; revised by fix2)
- The fetch and normalization code is committed: `docs/sources/tools/fetch_pins.py` (python3 standard library, HTTP GET only, no credentials). Its docstring defines the normalizer (version 1: UTF-8 decode, drop head/script/style/noscript/template/svg content, NFC, collapse whitespace), the `compare` classes and every exit code.
- For each source the script records HTTP status, raw-body sha256, normalized-text sha256, sizes, selected headers and date markers. The S01-S34 baseline is `docs/sources/fetch-baseline.json` (retrieved 2026-10-03T21:18Z). GitHub sources are fetched at the pinned commit (`raw.githubusercontent.com/<repo>/<sha>/<path>`) and the git blob sha1 is recomputed; all 7 match the pinned blobs.
- Primary pin (`pin_v2.primary`). Since fix2, 14 sources use the raw-body sha256: the 7 GitHub permalinks (S16-S19, S27, S29, S34; immutable by commit) and the 7 OpenBSD/OpenSSH pages (S01-S05, S10, S30), whose raw hash held from the v1 retrieval (2026-10-02T23:56Z) to the fix2 re-run (2026-10-09T05:31Z). The other 20 use the normalized-text sha256: CMS or static-site HTML (S06-S09, S11-S15, S20-S23, S28) and the `.md` variants of doc sites (S24-S26, S31-S33), whose bytes can change in a site rebuild without a text change. The raw hash is kept for all as evidence of the exact bytes fetched. fix2 moved S23 from raw to normalized (section "Pin changes in M00-T02-fix2").
- Reproducibility proof (executed, 2026-10-03): `fetch` run twice back to back gave 34/34 identical raw hashes and 34/34 identical normalized hashes and date markers (`docs/sources/fetch-repeat.json` vs `fetch-baseline.json`, `compare` exit 0), and the 27 snapshot files were byte-identical across the two runs. That shows stability over minutes. Over longer intervals: 21 sources kept their v1 raw bytes for about 21 h (v1 to v2; 13 did not), and the fix2 re-run after about 5.3 days found raw bytes unchanged for 19 and normalized text unchanged for 32 of 34 (`pins.json` `reproducibility`).
- v1 hashes. For the 28 HTML and GitHub sources, the v1 `text_sha256` came from an HTML-to-text script that was not retained, and the independent review could not reproduce it. It remains in `pins.json` as `pin.legacy_text_sha256_unreproducible` and must not be used as a drift detector. For the 6 `.md` sources (S24-S26, S31-S33), the v1 `text_sha256` equals the v2 raw-body sha256: v1 hashed the same raw `.md` bytes 21 h earlier. fix2 relabelled these 6 as `pin.legacy_raw_body_sha256_v1` (reproduced), following the recheck's `legacy_v1_hashes.out`. The `pin.value` fields that still held v1 text hashes (13 sources) now say "superseded". The v1 sentence "all 34 text hashes matched on re-fetch" is withdrawn as unverifiable.
- `compare` (revised by fix2) gives each source one class, with the HTTP status taken into account: IDENTICAL, RAW_ONLY (text and markers equal, bytes differ), MARKER_ONLY (text equal, a date marker moved), CONTENT (visible text changed, or a GitHub body whose blob sha1 is not the pinned blob), FETCH_FAILED (either side not HTTP 200, for example a bot-challenge 403; hashes not compared), MISSING, EXTRA. It also reports `primary_same`: whether the new file still matches the `pin_v2` primary hash in `pins.json`, which it must be able to read unless `--no-pins` is given. Exit 0 = all identical, 4 = text identical with only bytes or markers moved, 3 = fetch failure, 2 = content change or missing source; 1 = unreadable input, 64 = usage error. The v1 compare counted a moved date marker as a content change and ignored HTTP status. All requests are GET over https only, also after redirects.
- GitHub branch drift. `fetch` reads the pinned commit, so `compare` cannot see later changes on the branch the spec URL names. `fetch_pins.py upstream` GETs the raw file on that branch (the raw rendering of the spec URL; HEAD for repo-root URLs), compares its blob sha1 with the pin, and counts the quoted fragments still present. Exit 0 = no drift, 4 = drift with every quoted fragment still present, 2 = a drifted source lost a quoted fragment, 3 = fetch failure.
- Release tags. `pins.json` `tag_pins` records the commit each candidate release tag pointed to on 2026-10-09, read from the repository's public git ref advertisement (GET `https://github.com/<repo>.git/info/refs?service=git-upload-pack`, protocol v0, no POST). `fetch_pins.py tags` re-checks them. Tag names stay as labels.
- Excerpt attribution. `fetch_pins.py excerpts` checks that every quoted fragment of every `pins.json` excerpt occurs in its own source's pinned copy, and names any other source that contains a missing fragment (the S26 misattribution class). It exits 3 if any source could not be checked (a GitHub source without `--fetch-git`, or an excerpt with no quote). S05 and S21 had no quoted fragment, so fix2 added verbatim quotes from their snapshots. On 2026-10-09 every one of the 38 sources was checked and every fragment found (counts in the fix2 README).
- Immutable copy. GitHub sources: commit permalink plus blob sha1. The other 27 spec sources and A01-A04: a deterministic gzip of the normalized text in `docs/sources/snapshots/` (scope, verification and copyright note in its README; owner decision E8). The Internet Archive's read-only availability API (GET only, no save requests) returned a snapshot for 8 of 27 sources across two passes, and its answers were inconsistent between passes. Every snapshot it found predates the pin, and only S03's archived text matches the pinned normalized text (`docs/sources/archive-lookups.json`). Archive URLs are recorded as hints, not as the copy of record.
- Date markers kept from v1 where they exist: OpenBSD man page footer date, openssh.org Last-Modified, Microsoft ms.date and updated_at, Smallstep "Last updated" text, 1Password embedded dateModified. They are now extracted by the script.
- Candidate versions came from the crates.io API, the npm registry, the Go module proxy and `gh api` GET, and tag commits from git ref advertisements (fix2). No installs, no writes, no SSH or credential access, no fixture downloads.
- Claim check: each spec one-line claim was compared with the fetched text. "Supported" means the page text is consistent with the spec's one-line claim; it is not behavioral evidence for installed versions. The independent review checked this against live pages and confirmed all 34, apart from the misattributed S26 quote, which is now corrected.

- Telemetry is opt-in: the first setup command (`roost`, `fly`, `add`, `service install`) in a terminal asks once; nothing is sent unless `telemetry_enabled = true`. Endpoint counters (relay usage, hole-punching success, bytes moved) are sampled once a minute and pushed to iroh-services over an iroh connection, so the sending endpoint ID is visible to the collector.
- `pigeons service install` installs a system service (systemd, launchd, Windows SCM); the roost then runs as root and reads a machine-wide config (`/etc/pigeons/config.toml` or `C:\ProgramData\pigeons\config.toml`).
- `pigeons add` writes to `~/.ssh/config` (README example output) and the tool uses a dedicated `.ssh/pigeons_ed25519` keypair.
- Security model: anyone holding the endpoint ID can reach the SSH port; SSH auth still applies end to end.
- Fixture rule (inference from CLAUDE.md boundaries, not a Pigeons statement): any trial runs with HOME pointed at a scratch directory, never `service install`, telemetry answered or preset off. Release binaries: darwin aarch64/x86_64, linux aarch64/x86_64, windows x86_64. The documented install script is `curl | bash` from an S3 bucket; fixtures should use release assets or cargo instead.

## Reopen conditions
- `fetch_pins.py compare` against `docs/sources/fetch-baseline.json` (or `fetch-baseline-aux.json`) classifies a source cited by a still-open gate as CONTENT, or reports `primary_same=no` for it. Read `docs/sources/snapshots/<id>.txt.gz` to see what the pin said. MARKER_ONLY, and RAW_ONLY with `primary_same=yes`, are not drift. FETCH_FAILED means re-run.
- `fetch_pins.py upstream` exits 2: a GitHub source drifted on its spec branch and lost a quoted fragment. `fetch_pins.py tags` exits 2: a tag moved or is missing.
- A candidate ships a new minor/major release before the G02 selection is locked.
- Win32-OpenSSH (`PowerShell/Win32-OpenSSH`) publishes a release tag without "Preview", or `PowerShell/openssh-portable` changes its `LICENCE`. Iroh JS adds darwin-x64, or A02 changes the Go binding's status or platforms. Pigeons changes its ProxyCommand integration, telemetry or service behavior.
- spec section 19 is amended, or `docs/compatibility/matrix.md` cites a source not listed here or in the G03 source pins.

## Limits
- Normalized-text hashes depend on the normalizer: a change of Python's `html.parser` or `unicodedata` data could shift a hash without a content change. The baseline and the fix2 runs used Python 3.14.8. A mismatch should be checked against the snapshot before it is treated as drift.
- Long-interval stability is shown for one interval per source: about 21 h (v1 to v2), and about 5.3 days to the fix2 re-run. The auxiliary sources A01-A04 have only a same-day pair of runs.
- `upstream` reads the branch HEAD at one moment; it does not list the commits that changed a file. Release asset digests are not recorded (see Candidate dependency pins).
- The Internet Archive availability API gave inconsistent answers; absence of an archive URL is not proof of absence.
- Behavioral claims (E2 Match exec under `ssh -G`, OpenTUI under Node 26.4 versus Bun, Iroh JS on Intel macOS) are not tested here; they belong to G02, G07 and G09.
